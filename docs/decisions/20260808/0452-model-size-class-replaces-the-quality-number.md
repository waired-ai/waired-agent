# ユーザーに見せるのは品質の数値ではなくサイズクラス (20260808 04:52)

## Status
Accepted

## Context

`quality_tier` は「quality」と名のついた 1〜100 の数値として、トレイ、
`waired models ls --detail`、インストールウィザード、docs-site のカタログ表、
NAVI のセットアップウィザードに表示されていた。

#518（`docs/decisions/20260805/1427-quality-tier-is-a-curated-ladder.md`）が
これを「載せると決めた世代のパラメータ順を、出典付きの少数の override で補正したもの」
と定義し直した。実体は

    10·log10(params) − 5·log10(footprint_mb)

というカタログの 2 フィールドに対する算術で、**測定値ではない**。2 桁の数値を
「quality」と名付けて出すことは、データが支えていない精度の主張になる（#537）。

### 覆すことになる過去の決定

「生の数値を全ピッカーに出す」は明示的に裁定済みで、2 つのコードコメントに残っていた。

- private `waired`、`web/admin/src/lib/setup.ts` の `qualityNote` —
  「The raw number rather than a coarse scale (**owner decision**): it is the
  catalog's own value, and any **re-bucketing would have to be kept in step with
  it forever**」
- `internal/gui/tray/state.go` の `catalogSpecSuffix` — 「the review that asked for
  this asked for a quality value on every picker, and it is the raw catalog number
  rather than a coarse scale — a re-bucketing would have to be kept in step with
  the catalog forever」

この反論は**人が書く（authored）クラス**に対しては正しい。維持対象が増えるからである。

### 検討の過程で潰れた案

1. **tier の閾値でバンドを切る。** 「根拠が薄いから見せない」と言いながら、その数値を
   新しい線の根拠にすることになる。オーナー指摘により却下
2. **パラメータ数で切る。** MoE が順序を壊す。総パラメータはメモリの量であって品質の
   順位ではなく、28B を境にすると `qwen3.6-27b`（dense 27B）が最下位帯に落ち、
   `qwen3.6-35b-a3b`（総 35B / アクティブ 3.3B）が `glm-4.5-air`（総 106B）より下になる
3. **footprint そのもので切る。** 同じ理由で `--min-*` フィルタの意味が主張と逆になる。
   ただしこれは「ラダーの順序が正しい」を前提にした反論であり、1 で前提が落ちている

## Decision

ユーザー面に出すのは **`small` / `medium` / `large` のサイズクラス**とする。
これは**品質の主張ではなくグラフィックカードのクラス**である。

    small   ≤  8 GB   普及帯のカードで、重みをこぼさず動く
    medium  ≤ 32 GB   民生用の上位カードで動く
    large   それ以上   民生用カードでは動かない

`quality_tier` は**内部に据え置く**。自動選定の主ソートキー、`InstallQualityFloorTier`
との比較対象、`tier_override` の唯一の記録、`[1,100]` を要求する公開 proto フィールドで
あることはいずれも変わらない。ワイヤにも残る（NAVI の並び順の入力）。変わるのは
**描画するかどうか**だけである。

### 過去の決定への反論に答える形

新しいクラスは**著者が書くフィールドではない**。`proto/hostfit.ModelSize` が
`OllamaWeightsResidentMB` を 2 台の固定参照機に対して評価して導出する。モデルごとに
書き下すものが 1 つも無いので、「keep in step with the catalog forever」の対象が
存在しない。過去の裁定はこの形の再分類を排除していない。

### `OllamaWeightsResidentMB` を選んだ理由

**推奨ゲートが比較しているまさにその項**だからである。新しい式を組み立てる代わりに
これを呼ぶことで、境界が製品内で意味を持つ — バリアントが `small` であるとは、
「推奨ゲートが 8 GB のカードでこれを通す」ことと同義になる。

窓ではなく重みなのは、その関数自身が文書化している理由による。収まらない KV は
tuning がクランプする窓だが、収まらない重みはデコードのたびにシステム RAM から
読み直され、操作者が体感するのは後者である。

参照機は**カード**であってホストではない。Waired の容量判定は RAM と専用 VRAM を
合算する（2026-08-03 のオーナー決定、waired#1056）が、それは「あなたのマシンで動くか」
という別の問いに対する正しい答えであり、ここでは使えない。クラスはどのマシンでも
同じ意味でなければ、あるホストで書いたフィルタが次のホストで別の意味になる。

### 8 GB / 32 GB を選んだ理由

民生用グラフィックカードの普及帯と上限帯であること、そして**実カタログで線が隙間に
落ちる**こと。2026-08-08 時点の最接近は 8 GB 線に対して 7.4%（`qwen3.5-9b`、7,583 MiB）、
32 GB 線に対して 24.1%（`qwen3.5-35b-a3b`、24,873 MiB）で、**24,873 MiB と 48,721 MiB
の間には何も無い**。分布は large 7 / medium 7 / small 7。

`proto/hostfit/model_size_test.go` の `TestModelSize_ShippedCatalogClearsBothLines`
が 5% のマージンでこれを守る。線の近くに来たバリアントは、クラスがカードではなく
オーバーヘッド較正で決まる状態なので、必ず人が見ることになる。

### `small` / `medium` / `large` を選んだ理由

主張がサイズだからである。`low` / `high` は取り除いたばかりの「良い/悪い」の読みを
持ち込み直す。S/M/L はモデル規模の確立した三つ組であり造語ではない。

### モデルのクラスは最も軽いバリアントで決まる

行はファミリであり、その裏のビルドを選ぶのは我々である。最も重いビルドで分類すると、
実際に配るビルドなら載るモデルを「手が届かない」と読者に伝えることになる。
これは人からモデルを取り上げる方向の誤りである。

ただし `BestSize`（公開ノードが何を動かしているか）は**バリアント**で解決する。
軽重両方のビルドを持つモデルを、重い方を動かしているマシンについて軽い方で報告する
ことになるため。

### 不明はフェイルクローズ

重み注記の無いバリアントは空文字を返す。`SizeRank("")` は 0 で、あらゆる実クラスの
下に来るので、フロアは必ずこれを除外する。`proto/catalog.BestTier` の tier 0 が
既に持っている契約と同じ。空を `small` と読むのは waired-agent#364 の鏡像
（ゼロの推定値を確定した判定として読んだ欠陥）になる。

## Consequences

- **`--min-tier` は既存のワイヤフィールドでは表現できない。** クラスは tier の線とは
  一致しない（`glm-4.5-air` は tier 75 で `large`、`qwen3.6-35b-a3b` は tier 90 で
  `medium`）ので、tier のフロアではクラスを表せない。CLI・エージェントのゲート・CP の
  フィルタはいずれもクラスを比較する側へ移る。ピア間のワイヤは変わらない — ピアは
  今もモデル ID を広告しており、受け手が `BestSize` でローカルに解決する
- **表示面が減ることで失われる情報はない。** `NEEDS` 列・`FIT` 列・`recommended` の印は
  固定の参照機ではなくユーザーの実機に対して答えており、そちらの方が厳密に良い。
  クラスが必要なのは、見ることのできない他人のマシンを言い表す場面である
- **カタログ変更がクラスを動かすと差分に出る。** `TestModelSize_ShippedCatalog` が
  21 行の対応表を固定する。#522 が 2025 世代を退役させるとこの表が落ちるので、
  クラスの移動が意図されたものかを必ず見ることになる
- **`docs/reference/models.md` の生成 `品質` 列は残る。** maintainer 向けの数値ダンプで
  あり、#518 が `quality_tier` を tier_override の唯一の記録と定めた以上、そこは
  維持する。冒頭に「製品面には出さない」旨を注記する

## Alternatives considered

- **数値を消すだけでクラスを作らない。** `--min-tier` がユーザーに値を入力させる
  フラグである以上、参照できる数値がどこにも無くなると指定できなくなる。棄却
- **`--min-tier` ごと退役させる。** CLI フラグ 1 本と CP のフィルタ 1 行だけで GUI は
  無く、`auto` モードが「自分の最良を上回る公開ノードだけ使う」を計算で満たしている。
  検討したが、`explicit` モードの唯一の絞り込み手段なので残す
- **粗いスケールではなく相対表現。** ベンチマークの切替プロンプトで「品質が上がる/
  下がる」を出す案。消す理由が「測定値ではない」である以上、比較として出すのは同じ
  主張を弱く言い直すだけになる。棄却し、方向は周囲の文で述べる
- **2 段（コーディングに使える / 使えない）。** 確定済みの線は
  `InstallQualityFloorTier` だけなので最も正直だが、`--min-*` のフィルタとしては粗い。棄却
- **バンドをマニフェストに書く。** 過去のオーナー決定が排除したもの。維持対象が
  増える。棄却
