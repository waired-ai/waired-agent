# メモリの予算は推定のままにし、外れたときを安全にする (20260920 21:00)

## Status

Accepted

## Context

製品のメモリ予算は**推定**である。参照機 (Strix Halo、統合メモリ 128 GB、
Windows、Vulkan) では、予算が 98,304 MB で重み 95 GB 前後まで通すのに対し、
実際に読めたのは約 84 GiB までだった (#1443)。

いったんは機種ごとの定数で埋める実装を書き、取り下げた。機種が増えるたびに
コードと実機の往復が要り、未知の機種では外れ続けるためである。
オーナーの判断 (2026-09-20):

> 予算を切り詰めるのではなくて、例外処理を充実させるのはどうでしょうか?
> 今回のようにOSごとハングさせるんじゃなくて、足らなくなった段階で
> waired側で止めるような。

設計にあたり 3 OS の実機でメモリ圧のシグナルを測った
(`docs/knowledges/20260920/1900-os-memory-pressure-signals-3-os.md`)。
その結果が、この決定の形を決めている。

## Decision

**予算は推定のまま変えない。** 代わりに、外れたときの被害を 3 つの仕組みで
抑える。

**1. ホストを守る見張り (読み込み中)。** OS 自身のメモリ圧シグナルを読み、
critical が 10 秒続いたら読み込みを止め、エンジンを退役させる。判定は
「OS 自身が critical と言っている」か「空きが下限を割り、かつスワップが
急増している」のどちらか。**スワップ速度だけでは絶対に止めない** — 健全な
ホストも普通にスワップする (実測: アイドルの mac mini が 3.28 GB を
スワップに置いたまま、スワップアウトは 0)。閾値は大きめに取った
(32 MB/s。平常時の最悪 1.15 MB/s の 28 倍、実測のスラッシュ 640 MB/s の
20 分の 1)。**止めそこねる方に倒してある**: 早期の経路を外しても、OS 自身の
シグナルが少し遅れて拾う。

**2. 失敗の分類 (読み込み後)。** 見張りでは #1443 の落ち方は捕まらない。
あのホストは最後まで 28 GB 空いていて、ホスト側のシグナルは 1 つも動かない
からである。デバイス側が尽きており、runner が常駐化の段で落ちる。これは
エンジンのログの末尾から分類する。**分類できたエンジンは降格させず、
再起動の予算にも加算しない** (#1038 の先例に従う): エンジンは正常で、
合っていないのは重みの選択である。

**3. 記録と、その帰結。** 「このホストでこのビルドは載らなかった」を
`catalog.State.FailedLoads` に残す。キーは variant の content digest、
適用条件はエンジンの版・GPU・ドライバ・VRAM・RAM と、読み込みの形
(コンテキスト長・KV の型・並列数・backend)。帰結は 3 つ: 自動で同じ
読み込みをやり直さない、小さいビルドを勧める、人に伝える
(`waired status` / `doctor` / tray)。**小さい構成への再試行は塞がない** —
それがこの記録の起こすべき段下げだからである。

封じ込めは OS ごとに: Linux は `oom_score_adj` (fork/exec をまたいで継承
されることを実測済み)、Windows は Job Object のコミット上限 (実機検証が
条件)、macOS は公開 API に相当物が無い。

## Consequences

- 予算が外れている機種でも、製品は落ち方を選べる。ホストを道連れにせず、
  人に次の行動を伝えられる。
- 機種ごとの定数を増やさないので、実機との往復が要らない。新しい機種で
  予算が外れても、仕組みが同じように働く。
- 見張りは #1443 の落ち方を捕まえない。これは欠陥ではなく分担であり、
  そちらは分類が扱う。テストにその 2 つを取り違えないための契約を置いた。
- 閾値を大きめに取った分、遅く止まる場合がある。ホスト保護としては、
  正常な読み込みを殺すより望ましい。
- 判断が OS ごとに違う経路で成立する (実測: Linux は PSI、macOS はゲート+
  急増、Windows は低メモリ通知)。1 つの経路に依存していない。
