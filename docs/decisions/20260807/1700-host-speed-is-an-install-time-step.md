# ホスト速度の計測をインストール時の既定ステップにする (20260807 17:00)

## Status

Accepted

## Context

20260807 15:00 の決定（`1500-host-speed-on-the-wire.md`）でホスト速度は
ワイヤに載り、`waired inference status` と CP のデバイス詳細に出るように
なった。残っていたのは **いつ測るか** で、そこに二つの穴があった。

1. **ブラウザウィザードでは、選ぶ時点で数値が存在しない。** 計測の契機は
   pre-pull 経路（`applyHostCutoff`）と `setupApplyModel` の 2 箇所しか
   なく、前者はウィザードが操作中のあいだ最大 60 分保留され
   (`prePullHoldMax = setupDesiredFreshWindow`)、後者は人がモデルを
   指名したあとに走る。20〜45 GB をダウンロードするかを決める場面で
   数値が無いことが構造的に確定していた。

2. **同じインストールを測り直す契機が無い。** キャッシュはエンジンビルド
   のみをキーにしていたので、agent を更新してもエンジンが据え置きなら
   古い数値が残り続ける。ハードウェアを増設した場合も同じ。

waired#1099 のオーナー判断（20260807）は「これはインストール／`waired init`
のたびに実行されるべきステップであり、ハードウェアが同一だからスキップする
という処理は不要」。

## Decision

**計測は engine bootstrap の末尾で、無条件に走らせる。**
`bootstrapAfterEngineStart` は、エンジンが serving 状態で、かつすべての
インストール経路が必ず通る唯一の地点。ここに置くことで、ウィザード経由でも
CLI 経由でも、モデルを選ぶより前に数値が揃う。

置く位置はバックエンドプローブとチューニング検証の**後**。この 2 つは
エンジンを停止・再起動することがあり（#359 が同じ理由で全ダウンロードを
この下に移している）、計測中に再起動されると prefill が途中で終わり、
`Measured()` が false になって 3 分が黙って捨てられる。

非同期。`pullsWG` に登録するので `waitForPulls()` が従来どおり全体を
join でき、`hostSpeedMeasureMu` が後続の呼び出し（pre-pull / setup）を
待たせて 1 回に畳む。

**さらに、ホストが静かになるまで待つ**（`awaitQuietEngine`）。ダウンロード中
でもなく、serve reconcile も控えていない状態まで待ってから測る。これは CI が
教えてくれた:

- 起動直後に測り始めた結果、オペレータのモデルのダウンロードが終わる
  400 ms 前に計測が始まり、その完了が引き起こした reconcile の 3 ms 後に
  `connect: connection refused` で死んだ。#359 が言う再起動は boot tail の
  2 つだけではなく、`endPull` からの reconcile も同じことをする。
- インストール中に測った値は、そもそも輻輳を測った値になる。3 サンプルの
  中央値が唯一補正できないのがこれ。

`warmTarget`（`inference_warm.go`）が同じ理由で同じ待ち方をしている。

## ロックの分割（同じく CI が見つけた）

`Status()` は毎回のポーリングで publish 済みの値を読む。計測とフィールドを
同じ mutex で守っていたため、**計測が走っている間 `/waired/v1/inference/status`
が丸ごと止まった**。CI ホストでは 10 分 41 秒。installtest は
`curl --max-time 5` で読むので空文字が返り、「daemon published no
pinned_version / no engine mode」として落ちた。トレイも CLI もウィザードも
同じ経路を読む。

`hostSpeedMeasureMu`（計測の直列化・長時間保持）と `hostSpeedMu`（フィールド
のみ・leaf・短時間）に分けた。**読み手が待つロックを、エンジンへのリクエスト
を跨いで保持してはならない。**

**キャッシュのキーは「インストール」にする。** エンジンビルド（従来）に
加えて `state.HostSpeedRecord.AgentVersion` を見る。デーモンの再起動は
再利用、インストールとアップグレードは測り直し。

## Consequences

- ウィザードで「このパソコンは 1 往復 N 秒」を、モデルを選ぶ前に出せる。
  それを実際に出すのは CP 側（waired#1099 の PR B）で、この決定は
  数値がその時点で存在することだけを保証する。
- インストールのたびに ~1 GB のダウンロードと最大 3 分のエンジン占有が
  増える。プローブモデルは推奨要件未満のホストに提示される最小モデル
  （quality_tier 12）そのものなので、その 1 GB は捨て値にならない。
- **アップグレードのたびに測り直す。** 同じホスト・同じエンジンでも、
  agent のビルドが変われば測り直す。「そのビルドがそのホストで何秒か」が
  測っている量であって、前のビルドが出した数値はその証拠ではない。
- **残す穴**: 再インストールも更新もせずに GPU を挿したマシンは、古い
  数値を持ち続ける。キャッシュキーにハードウェア指紋を足す案は上の
  オーナー判断で不要とされた。GPU の増設は実際にはドライバ更新と
  Waired の更新を伴うことが多く、その時点で測り直される。
- `waired init` に強制再計測の経路は**足さない**。新規インストールでは
  bootstrap が先に測っており、init から強制すると同じホストを 2 回
  測ることになる（遅いホストで 3 分が 6 分になる）。「インストールの
  たび」はキャッシュキーが保証する。
