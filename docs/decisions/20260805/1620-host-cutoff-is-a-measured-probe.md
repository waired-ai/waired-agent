# 推奨要件未満の判定は、実測プローブ 1 本のターン時間で行う (20260805 16:20)

## Status
Accepted

## Context

waired-ai/waired#1056（オーナー決定 2026-08-03）は「拒否は確実な OOM だけ、
それ以外はすべて動くオプトインを伴う推奨」と定めた。#464（#497 で出荷）は
容量を総メモリの計算にし、**速度を入力から外した** — 使える速度入力が母集団
定数 `hostfit.BandwidthSystemRAMGBs = 60` しかなく、`ClassCPUOnly` はそこから
免除されていたため。#465（出荷済）は「推奨要件未満はラッチではなくデフォルト」
というユーザーから見える半分を作った。

#496 は速度を**実測**として戻すために書かれた: ~1 GB のプローブモデルを引き、
ブートベンチを走らせ、実測レートで推奨する。issue 自身のコメントが先に決める
べき点を挙げていた — プローブのレートが、それで順位付けする対象のレートを
本当に予測するのか。

ステージ 1 として実機計測を行った（記録:
`docs/knowledges/20260805/1513-probe-predicts-decode-rate.md` および
`docs/knowledges/20260805/1610-igpu-classification-three-layers.md`）。
結果、**予測しないことが分かり、同時に予測する必要がないことも分かった**。

決定的だった数字:

- CPU-only ホストの 1 ターン（21k 文脈）は、現在推奨される tier 89 の
  qwen3.6-35b-a3b で **227 秒**、カタログ最小の密モデル tier 30 で **186 秒**。
  同じ計測でカード機（qwen3.5-9b / 24 GB）は **17.8 秒**。
  **モデルを小さくしても救われない。これはモデル選定の問題ではない。**
- プローブモデル自身（qwen3.5-0.8b, 1 GB）の 1 ターンは
  **CPU-only 66.5 秒 / 24 GB カード 4.5 秒**。15 倍差が、外挿もルーフラインも
  `ActiveBytesPerToken` も使わずに直接出る。計測コストは 39.9 秒 / 4.3 秒。
- 逆に外挿は信用できない: 同じプローブからの 1 ターン予測は +1% / −8% の的も
  あれば +62% / −50% / **+93%** も出る。最後は GPU 機を 30 秒閾値で誤って
  切る側の誤差。

## Decision

1. **プローブは「どのモデルか」ではなく「このホストが推論エンジンを有用に
   回せるか」を答える。** ホスト単位の足切りであり、モデル順位付けの入力では
   ない。（オーナー、2026-08-05）
2. **判定量はプローブ自身の 1 ターン所要時間**
   `P/prefill + (P/21)/decode`。他モデルへの外挿は行わない。
3. **閾値は 60 秒**。実測の 66.5 秒（CPU-only）と 4.5 秒（カード機）を、
   両側に 1 桁の余裕をもって分ける。中間ハードウェアでの実測が出た時点で
   見直す。
4. **計測は深さ付きで行う**（~21k 文脈でプレフィルとデコードの両方）。浅い
   200 トークンのブートベンチは実セッションのデコードを CPU で 24〜60%、
   GPU で 10〜16% 過大評価する。`cmd/waired-agent/inference_bench_depth.go`
   (#624) が既にこの形。**プロンプト先頭にはサンプル毎のノンスを置く** —
   ollama の接頭辞 KV キャッシュは同一プロンプトの 2 回目に
   `prompt_eval_count` を満額返しつつ所要時間ほぼ 0（実測 697,222 tok/s）に
   するため。
5. **プローブモデルは qwen3.5-0.8b**（1.0 GB, q8）。フロア分類器として採点
   すると両レッグ 22/22 で、granite4-350m は CPU で 9/11（2 件ともフロア直下
   の false-block）、定数 60 は 16/22。
6. **判定は `SelectInstallModel` の `ok=false` 経路に入れる**
   （→ `BelowRecommendedSpec` → #465 のローカル推論オフ + オプトイン）。
   `OllamaRecommend` 経由にしてはならない: `model_picker.go:276-285` の
   `narrow` は全候補を落とすフィルタに対して no-op（`if len(pass) > 0`）
   なので、捕まえたいホストで黙って何もしない。
7. **#496 のスコープ項目 2（実測レートを推奨に流す）は取り下げる。** 実測
   したところ選定を 1 つも変えず、デコードフロアを当てると 24 GB のモデルを
   落として 45 GB のモデル（qwen3-coder-next-80b-a3b, tier 86, 実測なし）を
   選ばせる。デコード tok/s は判定器として誤り。
8. **ハードウェア分類の是正は前提にしない。** 3 層（プロファイラ /
   `hostfit.Class()` / エンジン）が食い違っており、`hostfit` には
   「integrated」の概念が無く、iGPU を検出した方が検出しないより速いホストに
   見える。プローブは構成されたままのホストを測るので、この食い違いに依存
   しない。分類側の是正は #287 が持つ。

## Consequences

- CPU-only 機と、エンジンが iGPU を捨てる iGPU のみの機は、既定でローカル
  推論オフになり、`waired inference on` のオプトインが残る。#465 が出口の
  UI を既に持っている。
- Strix Halo は影響を受けない。エンジンは gfx1151 を許可し、プロファイラは
  CPU 型番から `UnifiedMemory` を立て、プローブは速い数字を出して通過する。
- `ActiveBytesPerToken`、`OllamaRecommend`、`BandwidthSystemRAMGBs`、
  `InstallQualityFloorTier` はいずれも変更しない。MoE の過大評価
  （同アクティブバイトの密モデル比 4〜37% 遅い）は記録に残るが、この判定は
  それを通らない。
- 「どのモデルを推奨するか」は #466 が持つ。プレフィルは CPU ターンの
  50〜70%、GPU ターンでも 32〜52% を占め、総パラメータでもアクティブでも
  スケールしない（30B-A3B は 3B 密ではなく 9B 密の隣に座る）ので、
  そこには 1 ターン秒数の基準が要る。

## Why not the alternatives

- **#496 を書かれたとおり実装する（実測レートを推奨ゲートへ）** — 計測で
  否定された。上の Decision 7。
- **ハードウェア分類を直してから判定する** — #287 を前提にすることになり、
  かつ 3 層の食い違いは分類の精度では消えない（エンジンが何を使うかは
  分類の外にある）。
- **浅いプローブのまま使う** — 実セッションを最大 60% 過大評価し、GPU 側では
  1 GB モデルが固定コストに支配されて 2 倍過小評価する。どちらの誤差も
  閾値をまたぐ。
- **閾値をデコード tok/s にする** — プレフィルが CPU ターンの 50〜70% を
  占めるので、待ち時間の半分以上を見ないことになる。
