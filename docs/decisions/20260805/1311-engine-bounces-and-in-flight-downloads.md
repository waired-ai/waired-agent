# エンジンのバウンスと進行中のダウンロードは、3 層で分離する (20260805 13:11)

## Status

Accepted。#359 の Option 1（順序）と Option 2（リトライ）を採用し、Option 3
（`reconcileEngineServe` の共有ゲート）は採らない。Option 2 はエラー分類ではなく
**エンジンのプロセス世代**で実装する。

## Context

`ollama pull` は `ollama serve` の**クライアント**である。エンジンを止める経路は
すべて進行中のダウンロードの子プロセスを非ゼロ終了させ、`runPullJob` はそれを
そのモデル自身の失敗として記録していた。#305（PR #358）は 4 経路のうち
1 つ（pull 完了が起こす pending-swap バウンス）だけを `endPull` まで繰り延べ、
残りは意図的に据え置かれた。

起票（2026-08-01）以降に前提が 2 つ動いている。これは方針に直接影響する。

- `runPullJob` に 3 回リトライが入った（#306 / PR #378、2026-08-02）。各試行の
  先頭で `EnsureRunning` を叩くので、バウンスで殺された DL は数十秒後に再開する。
  **「必ず failed になる」はもう最悪ケースではない。**
- #136 のモデル世代レバー（`DesiredModelGen` / `SetupProgress.ModelGen`）が着地し、
  赤くなったモデル行に手動リトライ手段ができた。

したがって残る実害は「3 回しかない試行予算が無関係な理由で削られ、その先で
本物の transient に当たると failed に落ちる」ことに絞られる。ブート末尾は
backend fallback と tuning degrade で**自力で 2 つ削れる**ので、ここが最悪。

## Decision

### 1. ブート末尾は、1 バイトも要求する前に自分の再起動を済ませる

`bootstrapAfterEngineStart` の backend probe と tuning verify を、モデルの
dispatch より**前**に動かす。これは #359 の 4 経路のうち唯一の**自傷**ケース
——自分が投げた pull を自分で殺す——で、しかも `engineBootstrapOnce` が
このテールを 1 プロセス 1 回に latch するので、被害が固定される。

どちらの手順も dispatch の結果に依存しない（probe は `/api/ps` と既存タグ、
verify は起動時に凍結した `bootPlan`）ので、並べ替えても観測するものは変わらない。
代償は、probe が走るホスト（Strix Halo Linux）で pull 開始が最大 3 分遅れること。
エンジンを落ち着かせてから落とすほうが正しい。

なお `if !p.bootPlan.tuned { return }` は条件式に反転させた。dispatch が下に
移ったので、ここで return するとダウンロードごと飛ぶ。

### 2. 容量再チューンだけは繰り延べる

`ApplyConcurrency` は、DL 進行中なら既存の `retuneDeferred` を立てるだけにし、
`endPull` に発火を任せる。#359 は「CP の容量変更を DL の後ろに飲み込ませるな」と
書いていたが、これは**飲み込まない**: 目標値は `desiredParallel` に記録済みで、
繰り延べた reconcile は最新値を読み直す。実際に効く admission cap
（`Server.SetCapacity`）は呼び出し側が非破壊に適用済みで、遅れるのはエンジンの
`OLLAMA_NUM_PARALLEL` だけ。CP の容量フレームは起動直後に来るのが普通で、
ちょうどブートの巨大 DL とぶつかるので、ここは繰り延べる価値が最も大きい。

ゲートは `requestEngineReconcile` の中ではなく**呼び出し側**に置く。
暗黙に全経路を繰り延べる作りにすると、下の 2 つを巻き込むため。

### 3. 残りは「無罪リトライ」で受ける — エラー分類ではなく、自分の停止回数で

繰り延べてはいけない経路が 2 つある。

- **クラッシュ復旧**: エンジンは既に死んでいて DL はどのみち死ぬ。復旧を
  マルチ GB のダウンロードの後ろに置くのは端的に悪化。
- **オペレータのモデル切替（重みがディスク上）**: 明示的な操作を、本人が
  頼んでもいないダウンロードの後ろに数十分置くことになる。

そこで `runPullJob` 側で受ける。#359 の Option 2 は「接続エラーとレジストリ
エラーをどう区別するか」という難問を抱えていたが、**エラーを分類しない**：
`OllamaAdapter` は既にプロセス世代 `procGen` を持っている（`superviseChild` が
「意図的な停止」と「クラッシュ」を区別するのに使っている）。これを公開し、
各試行の前後で読む。**世代が動いていれば、止めたのは我々**である。

その試行は試行予算に計上せず、失敗テキストも記録せず、backoff も置かない
（置くべき待ちは次の周回の `EnsureRunning` が再起動に join することそのもの）。
上限は `enginePullBounceGrace = 2` ——ブート末尾の最悪ケースが 2 回だから。

この形なら、**将来追加されるバウンス経路も自動的にカバーされる**。すべて
アダプタの `Stop` / spawn を通るからで、これは Option 2 が「including ones
added later」と書いていた性質を、エラーテキストに頼らずに満たす。

### 4. Option 3（`reconcileEngineServe` の共有ゲート）は採らない

issue 自身が指摘した罠——ループ先頭の `swapPending.Swap(false)` が破壊的なので、
その後ろに繰り延べを置くとオペレータの切替が黙って消える——を避けるには、
ゲートを swap の上に置くか意図を書き戻すしかない。上の 2 と 3 で、置くべき場所に
置くほうが読める。

## Consequences

- probe が走るホストでは、ブートのダウンロード開始が最大 3 分遅れる。
- 容量変更は DL 完了まで反映されない（admission cap は即時のまま）。
- 1 回のダウンロードが最大 `modelPullAttempts + enginePullBounceGrace` = 5 回
  `ollama pull` を起動しうる。無罪リトライは backoff を置かないので、
  エンジンが再起動ループに入っていても余計に待たない。
- **カバーしないもの**: 進行中のダウンロード自体を止める手段は依然として無い。
  オペレータがトレイからモデルを切り替えても、走っているダウンロードは走り切る
  （#379 の決定ログ参照。キャンセルは採っていない）。無罪リトライは「殺された
  ダウンロードを立て直す」ものであって、「不要になったダウンロードを畳む」もの
  ではない。
- `procGen` は今後 `superviseChild` 以外にも読まれる。クラッシュで動かない性質は
  両方の読み手が依存しているので、`internal/runtime` 側にテストを置いた。
