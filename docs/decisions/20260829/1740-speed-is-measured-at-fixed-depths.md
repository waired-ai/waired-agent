# 速度は全ホスト共通の固定の深さで測り、制約として並びに入る (20260829 17:40)

## Status
Accepted。オーナー裁定 2026-08-29（waired-ai/waired-agent#1127, #1128）。

## Context

ピア選択に「そのターンが人にいくら掛かるか」の項が無かった。rc4 のレビュー
メッシュで、engine 無しホストの 3 万トークンの初回ターンを、一番大きいモデルを
持つピアが **9 分 10 秒**かけて返した。同じ人の別のマシンは 43 秒で返している
（waired-agent#1082）。しかもそのピアは品質と速度を交換したのではなく、カタログ
自身の `quality_tier` でも負けていた（35B-A3B が 90、122B-A10B が 83）。

#1040 でピア脚が「働いていると言っている間は待つ」ようになったので、並びの選択が
そのまま人の待ち時間になった。

## Decision

### 深さは定数にする

prefill スループットは深さに依存する。このリポジトリの実測（同一機体・同一モデル、
`docs/knowledges/20260805/1830-ollama-prompt-depth-two-traps.md`）:

| 実処理深さ | prefill |
|---|---|
| 11,526 | 833 tok/s |
| 21,247 | 583 tok/s |

1.84 倍深いと 30 % 遅く読める。同ノートの結論は「**浅いプレフィルはホストを速く
見せる**」。

この実装の最初の草稿は、オーナーが挙げた 3 条件（キャッシュ量超え・バッチサイズ
以上・ブースト時間超え）を満たすために**ホストごとに深さを変えて**いた。それは
速いピアを深く、遅いピアを浅く測ることになり、**比較したい量そのものと深さが相関
する** — 交絡である。しかも偏りの向きは、このプログラムが防ごうとしている
「遅いピアが選ばれる」方向だった。

なので深さは全ホスト共通の固定の段 **4,096 / 8,192 / 32,768** にする。これは
`hostfit.HostCutoffProbeDepthTokens` が固定である理由（"the point of a FIXED
probe is comparability"）を、serve しているモデルに適用したもの。

2 の冪なのは、この製品が設定するプロンプトバッチが全部 2 の冪だから
（llama.cpp 既定 2,048 / vLLM 4,096 / 70 GiB 以上の vLLM 8,192）。整数倍でない
深さはエンジンに端数バッチを走らせ、その誤差は**ホストごとに違う**ので相殺しない。

3 条件は深さ以外で満たす。ブーストは**プロンプトを伸ばすのではなく繰り返し**で
抜ける（統計的安定の要求と同じ手段）。バッチは最上段が最大バッチの 4 倍。

**最下段 4,096 だけは 70 GiB 以上の vLLM ホストでバッチ未満**になる。そのホストは
速いので 8,192 以上まで登り、4,096 が使われるのは「そこまでしか登れなかった遅い
ホストとの比較」に限られる — 差が大きいので押し下げられても順位は覆らない。
最下段を 8,192 にしなかったのは、54 tok/s のピアが 3 分の予算で 1 本しか取れず、
突き合わせる相手のない読みになるため。

### 比較はラウンド単位で 1 つの深さ

ホストは登れた段を全部 publish し、requester は**両者が到達した一番深い段**で
比べる。ただし**ペアごとではなくラウンドごとに 1 つの深さを先に決める**：ペア
ごとだと A が B に勝ち C に負ける関係が非推移的になり、`sort.SliceStable` に
非推移的な比較を渡した結果は不定である。

### 予算を超えたら下界

3 分（オーナー裁定。init はこの計測を待つ）。最下段すら終えられないホストは
**上界**を publish する — 「その時間で `Depth` トークンを終えられなかった」は事実
であって推定ではない。これは #579 のオーナー裁定（2026-08-09）が
`TurnFloorSeconds` について既に決めた形で、下界は計測値に混ぜず別フィールドに置く。

### 速度は制約であって置き換えではない

並びは `prefer` で 2 つのキーの順序が入れ替わるだけで、**キーの集合は同じ**:

```
prefer=size  : … → priority → [床] → score → speedBucket → errorRate → …
prefer=speed : … → priority → [床] → speedBucket → score → errorRate → …
```

`score` は `speed` の下に**残す**。速度キーは比較可能な読みがある相手しか分離
しないので、無いところでは並びは従来どおりになる。これが
`docs/decisions/20260822/0218-residency-breaks-ties-only.md` の nil ルール
（計測していない相手を罰しない）を並びとして表したもの。

速度キーは **25 % 帯にバケットする**。調査した全システムが標準の順序を覆すのに
余裕を要求している（Cassandra の `dynamic_snitch_badness_threshold`、MongoDB の
`localThresholdMS`）。加えて連続値だと `RankTier` が常に別々になり、#880 の常駐
同点判定（同一 tier の中でのみ効く）が黙って退役する。

**未計測のピアは最良の bucket を与える**。最後に置くと nil ルールに反し、しかも
publish されたレートを取ってくるのはプローブなので、最後に置かれたピアは永久に
測られない。Elasticsearch の adaptive replica selection が同じ理由で同じことを
している（選ばなかったノードのスコアを押し上げ、飢餓を防ぐ）。

## Consequences

- **ホストは自分の速さを知るまでメッシュの仕事を受けない**（オーナー裁定、
  kubernetes の readiness probe の形）。`EngineReady` には載せられない — その述語は
  ベンチ自身の入口ゲートでもあるので、そこに掛けた計測は起動できない
- 計測は**一発勝負ではなくループ**。boot ベンチは `EngineReady` ゲートで一度きり
  発火し、約 60 秒で起動する vLLM ではそのレースをほぼ毎回落とす（実測 82 回中
  5 回完走、waired-agent#1150）。同じ形に乗せていたら丸ごと相続していた
- serve している variant が変わったら publish は止まる。古い数値はこのホストが
  もう動かしていないモデルの数値である
- 20260822/1935「実測は推奨の入力に戻り、梯子は 1 本になる」の**未完の半分**が
  埋まる。あの決定はモデル推奨には届いていたが、ピア選択には届いていなかった
