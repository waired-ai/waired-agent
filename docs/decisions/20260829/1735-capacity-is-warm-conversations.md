# Capacity は「温存できる会話数」であって復号の速さではない (20260829 17:35)

## Status
Accepted。オーナー裁定 2026-08-29（waired-ai/waired-agent#1126）。

## Context

ホストがメッシュに広告する入場上限は、ルーティングが必要とする問いとは別の問いに
答えていた。

```
Capacity = max(1, floor(decode_tokps / 30))
```

`NumParallel` でも `RecommendedMaxParallel` でも**一度も clamp されない**。
120 tok/s のホストが 4 を広告する一方、そのエンジンは `OLLAMA_NUM_PARALLEL` 1
（文脈長を犠牲にせず倍にできる場合で 2）で起動している。そのエンジンでは
**スロットが KV 保持の単位**なので、3 本目と 4 本目は 1 本目と 2 本目の
プレフィックスを追い出す。喪失の代償はコールドと同じ（2.57 s 対 35.38 s、
コールド 33.85 s）。

復号スループットは、この製品が運ぶトラフィックの軸としても誤り。コーディング
エージェントの初回ターンは prefill 支配で、実測 550,166 ms の応答ヘッダに対し
復号は 709 ms（waired-agent#1082）。#624/#764 も起動ベンチについて同じことを
言っている。

## Decision

> Capacity と保持できる会話数を一致させるのが、コーディングエージェント用途を
> 中心とする waired には適切でしょう（オーナー、2026-08-29）

割る対象は**窓**（同、「窓にしましょう」）。

2 つのエンジンは同じ量を別の場所に持つので、**片方をもう片方に模さず、それぞれが
実際に持っている場所から読む**:

- **ollama** は KV をスロットに分割し、各スロットが 1 つの窓を保持する。**スロット
  数がそのまま答え**。runner が実際に serve している `-np`（#763/#846 で読み戻し
  済み）を最優先し、次に要求した値、次にサイジングの上限
- **vLLM** は内容でハッシュした 1 つの共有プールなので、**プールを serve 窓で
  割った数**。プールは起動時のログ行から読み戻す

窓で割るのは、ollama のスロットが窓 1 つ分を予約するからで、それが 2 つのエンジンに
同じ意味を持たせる。実際の会話は窓より短いので保守側に外れる。

## Consequences

- **2 つのフィールドの意味が分かれる。** `Capacity` は「温存できる会話数」、
  `CapacityUsed` は「走っているリクエスト数」。アイドルだが温かい会話は
  `CapacityUsed` に数えられないので、`capacity_used < capacity` は
  「温かい枠が空いている」を意味しない
- `waired status` / `waired doctor` の `%d/%d slots in use` は**分数をやめた**。
  分子と分母が別の単位になったため
- **数値は版ごとに読み戻す。** 同一 argv・同一ホストで vLLM 0.24.0 が 393,709
  トークン、0.28.0 が 339,160（2 系統で独立に再現）。ログ行が無ければ
  `unmeasuredCapacity = 1` に落ちる
- `avgCodingAgentTokRate` は退役。値が誤っていたのではなく、モデル化の対象が誤って
  いた
- ollama ホストの広告値が下がる。過剰入場の是正だが、1 台のピアが吸収できる同時
  サブエージェント数は減る（#828, `demoteBusySticky` の重要度が上がる）
