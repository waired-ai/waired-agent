# 退役ワークリストの線を「全試行で失敗」から失敗率の信頼下限に変える (20260803 14:54)

## Status
Accepted

## Context

`internal/catalog/agentgrade.json` には合否ルールが 2 つある。

| | 場所 | 中身 | 消費者 |
|---|---|---|---|
| A. Grade（保存キー名は `verdict`） | `internal/agentgrade/probe.go` | ケースの Verdict が 1 つでも失敗系なら `fail` | `waired models check-agent` の終了コード／人間 |
| B. 退役ワークリスト | `internal/catalog/agentgrade.go` `failsEveryTrial` | あるケースが `Failed >= Trials` | `--require-pass` |

A が試行数の関数であることは #446 で記録済みで、そこから「判断は grade では
なくレートで下す」が導かれた。**`--require-pass` を有効化できないのはこの A の
せい**、と #322 のコメントは書いたが、実際に `--require-pass` が見ているのは
A ではなく B だった。B はすでにレート規則になっている —— ただし閾値が
**100% ちょうど**という特殊値で。

その線には擁護できない性質がある。**24 回中 24 回失敗は対象、24 回中 23 回
失敗は対象外。** まぐれ 1 回で絶望的なモデルがワークリストから消える。
そしてもう一つ、`Failed >= Trials` はレートのように読めてレートではない ——
**2 回中 2 回と 24 回中 24 回はどちらも 100% で、証拠なのは片方だけ**。

## Decision

**B の線を、失敗率そのものではなく失敗率の信頼下限に置く。**

```go
const RetireFailureRate = 0.5
func failureRateLowerBound(failed, trials int) float64  // Wilson 片側 95%
```

あるケースの下限が `RetireFailureRate` を超えたときにワークリストへ載る。
`Failures()` は前提条件だった `Verdict == fail` を落とし、カウントだけで判断する
（カウントが主張であって、verdict はその代理だった）。カウントを持たない
旧レコードは従来どおり保存 verdict にフォールバックする。

### 点推定ではなく下限を使う理由

**n を規則そのものに埋め込むため。** この一連の作業で分かった中心的なことが
「3 試行での pass はそこまで探さなかった以上の意味を持たない」であり、
`failed/trials` に対して閾値を引くのは同じ間違いを一段上で繰り返すことになる。
Wilson なら、標本が小さいほど下限は下がる ——「証拠が足りないので消さない」が
規則から自動的に出てくる。副次的な保証として、**試行数を増やすことは
エントリをワークリストに載せる方向にしか働かない**（測定を減らして外すことが
できない）。

### 閾値 0.5 の根拠

1. 実測データで **0.304（qwen3.5:9b）と 0.899（qwen2.5-coder:0.5b）の間**が
   ファイル最大の空白で、3 倍のマージンがある。
2. `k == n` のとき下限が 0.5 を超えるのは **n≥3 ちょうど**（n=2 で 0.425、
   n=3 で 0.526）。`DefaultTrials = 3` と一致するので、**現行
   `failsEveryTrial` を、import が受け付けるすべての試行数で再現する**。
3. カタログから項目を消すのは「成功より失敗が多い」という主張であり、
   それはレビューで人が擁護できる文になっている。

これより低い線は、残す理由のあるモデルを巻き込む —— qwen2.5-coder-3b は
インストール品質フロアを定義していて 0.167、granite4-350m は CI フィクスチャで
0.105、qwen3.5:9b の 0.304 は上流のパーサ不具合（ollama/ollama#16383）であって
重みの問題ではない。

### A は据え置く

`models check-agent` の既定は n=3 で、この標本数ではどのレート則も
「1 回失敗 → fail」と一致するため挙動が変わらない。一方 grade 側は
5%/10%/15% のどこに線を引いてもデータ点と数 % 差の際どい勝負になる。
**verdict は「計測時にプローブが言ったこと」＝ provenance と位置づけ、
判断はカウントを読む**、で一本化する。

## Consequences

- **保存データは 1 行も変わらない。** ワークリストは
  `qwen2.5-coder-0.5b-instruct` 1 件のまま。ゴールデンテストがこれを固定する
  ので、次に閾値を動かす人は自分が何の削除を提案したかをその場で知る。
- 新たに捕まえるのは、旧ルールがまぐれ 1 回で見逃していた 23/24 級の失敗。
- 逆に n=2 の全失敗は**対象外になる**（旧ルールより厳しい）。import は
  `Trials < 2` を拒否しているので、実害のある差ではない。
- `catalog-tool agentgrade` が、記録のある全 variant の「最悪ケースの
  failed/trials と下限」を最悪順で表示するようになった。ストアの `notes` が
  "READ THE RATIO, NOT THE VERDICT" と叫んでいるのに、ツールがワークリストしか
  見せていなかったので、**主張ではなく表示で解決した**。
- **`--require-pass` は引き続き無効のまま。** 有効化すると 0.5b で確定的に
  赤くなる（このチェックはモデルを走らせない静的なファイル読みなので、
  フレークではなく確定的に赤い）。赤を消すには「0.5b の提示をやめる」か
  「ゲートの適用範囲を絞る」かが要り、どちらも計測ルールではなく製品判断
  （極小ホストに何を出すか）なので分けて決める。
- #458 の retry はこの判断に影響しない。retry が発火するのはエンジンのパーサが
  500 を上げるか、ストリームが無言で切れるクラス。0.5b は HTTP 200 で地の文
  （提示されていない名前）を返す別のクラスで、実測でも retry 後 24/24 のまま
  動かなかった。
