# 判定はクラス別に数える。最悪ラベルとプールされた失敗数だけでは、方針変更が測り直しを要求する (20260803 20:26)

## Status
Accepted

## Context

`warn_invalid_tool_arguments`（#455）は「暫定的に、意図して」警告として導入され、
昇格の条件は **「チェックが入った状態で 1 度スイープが回ってから」** と書かれていた。
#467 がそのスイープだった。それでも昇格は判断できなかった。

理由はストアの形にある。1 ケースが持つのは

```go
Verdict string  // 全試行で最悪のクラス 1 つ
Trials  int
Failed  int     // 失敗クラスを全部プールした数
```

の 3 つで、警告はそのどちらにも入らない。したがって

* 最悪が失敗のケースでは警告は **完全に不可視**。`{fail_no_tool_call, 24, 1}` は、
  残り 23 回が綺麗だったのか 23 回とも警告だったのかを区別しない。
* 最悪が警告のケースでも、**存在しか記録されない**。1 回か 24 回かが分からない。

そして後者が答えを決める。昇格は警告試行を失敗の列へ移す操作で、退役ラインは
24 試行で **17/24** から。1〜2 回なら何も起きず、17 回以上なら退役提案になる。
ファイルにはその区別が無い。

`Failed` を後から計算し直すこともできない。**昇格が置き換えようとしている規則の下で
計算された値**だからである。つまり測り直しは避けられない。しかしクラスを数えないまま
測り直せば、同じ問いにもう一度答えられないまま終わる。

## Decision

**プローブが全判定クラスを数え、その集計をストアの一次記録にする。**

`Probe.Run` はケースごとに 3 つの並行マップ（`seen`＝ぶれ判定、`ran`、`failed`）を
持っていた。これを `map[Verdict]int` 1 本に畳み、`Trials` / `FailedTrials` /
`Flaky` をそこから **導出** する。同じ事実の置き場が 3 つあれば食い違えるし、
3 つのどれもクラスを数えていなかった。集計は `Result` → レポート → `CaseOutcome`
を `verdicts` として流れる。**欠落は「不明」であって 0 ではない**（`Trials == 0`
と同じ読み方）。レート表は該当行に `(not counted)` と出す。

プールの規則を 2 つ決めた：

* 2 トランスポートの集計は **足す**（試行数と同じ扱い）。
* 片方がカウンタ以前の実行なら **集計を落とす**。24 試行の横で 12 に合計される
  集計は「古い実行が混ざっている」ではなく「12 試行が判定不能だった」と読める。
  それは起こり得ない状態で、不明のほうが正直。

あわせて `--sweep-targets` と `scripts/dev/agentgrade-sweep.sh` を入れた。
カタログ全体の測り直しは 17 バリアント × 2 トランスポート = 34 回で、手打ちの
リストは 1 本落ちる／片方の経路でしか測られない事故の入口になる。対象は
`--check` と同じ規則でマニフェストとストアから導出する。

## Consequences

### 昇格は「無害」と判定できるようになった（実施は別 PR）

スイープ後の実測。警告が出た 13 ケースすべてで、昇格後の下限は退役ライン 50% に
届かない：

| ケース | 失敗 | +警告 | 下限 |
|---|---|---|---|
| granite4-350m / search-then-edit | 7 | +6 | 17% → **38%** |
| qwen2.5-coder-3b / search-then-edit | 6 | +3 | 14% → 23% |
| gpt-oss-20b / search-then-edit | 0 | +3 | 0% → 5% |
| 他 10 ケース | | +1〜2 | いずれも 3% 以下 |

つまり #455 が塞いだ盲点は実在した（51 ケース中 13 件、導入時の実測ゼロとは違う）
一方で、**昇格しても退役ワークリストは 1 行も動かない**。

昇格自体をこの決定に含めなかったのは、それが別種の変更だから。判定値の文字列
`warn_invalid_tool_arguments` は**ストアに保存されている**ので、`warn_` のまま
失敗として数えると `"verdict": "warn_...", "failed": 13` という読めない記録が残る。
リネームを伴う方針変更であり、4 バリアントの Grade が pass → fail に変わる。
そして分けられる決め手は、**この決定が入れば昇格に GPU が要らない**こと——
クラス別集計から再計算できる。それがこの計測器の存在意義そのものなので、
順番に出して実演する。

### 散文の陳腐化ガードが 1 PR で効いた

#475 で入れた `TestRatesCitedByRetireFailureRate`（`RetireFailureRate` の根拠が
名指しするレートを出荷ストアから読み直す）が、次のスイープでそのまま発火した。
引用していた 3 つの数字が全部動いていた（3b 23%→14%、granite4-350m 14%→17%、
qwen3.5-9b 5%→1%）。#467 のときは黙って古くなったので、これは想定どおりの働き。

### 0.5b の失敗の形が変わった（率は同じ）

`qwen2.5-coder-0.5b` は 2 回のスイープで **同じ 90% の下限**、**違う症状**を示した。
以前は「パーサが回収できないテキストとしてのツール呼び出し」、今回は
「ツール構文が一切無く、代わりに**答えを捏造する**」——ファイルを読めと言われて、
知りようのないホスト名を断定する。withhold の根拠としてはむしろ強くなったので、
マニフェストの理由文を実測に合わせて更新した。

退役ワークリストが 2 回のスイープで同じ 1 行を選び続けたことは、
`RetireFailureRate` が満たすべき安定性の証拠でもある（「毎回違う集合を消す」が
旧規則の欠陥だった）。
