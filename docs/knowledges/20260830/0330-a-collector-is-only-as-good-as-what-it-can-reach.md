# 収集器は「届く範囲」までしか良くない (20260830 03:30)

## Issue

#1158 — PR ごとに回る 3 OS の install test が、失敗時に何も残していなかった。
`installtest.yml` に `if: failure()` ステップも `upload-artifact` も 1 つも無く、
赤いレグの証拠は「ハーネスが死ぬ前に job log に刷った分」だけだった。

直す過程で、全 24 ワークフローを掃討した。

## Learnings

### 1. 収集器を書いても、届かない場所は増えない

`collect-engine-diag.sh` は #1112 で 1 本に統合済みで、3 OS で動き、
存在しないファイルは黙って飛ばす。**それでも証拠が採れていない場所が 4 つ**あった。
理由は全部「収集器の質」ではなく「**到達性**」だった:

| 型 | 実例 |
|---|---|
| 収集ステップが 1 OS に固定されている | `daemon-engine` は 3 OS 全部でエンジンを入れるのに、収集は `&& matrix.os == 'windows'` |
| 対象ファイルが消える | macOS ハーネスの `$WORK/init.log`。`WORK="$(mktemp -d)"` で、`cleanup()` の `rm -rf` が **EXIT トラップと `it_die` の両方**から走る |
| upload の条件が失敗と無関係 | `catalog-radar.yml` は `DRY_RUN == 'true'` のときだけ upload。定期実行が赤くなると何も残らない |
| 呼ばれていない | `sac-audit` は同じハーネスを走らせるのに収集器を呼んでいない |

**緑からはこの 4 つが全部同じに見える。** 収集ステップは失敗時にしか発火しないので、
「収集器を足した」PR が緑でも、それは何も証明していない。

### 2. `mktemp -d` は「ワークフローが再構成できない名前」

Windows の双子は `%TEMP%\waired-installtest-win` という**固定**パスなので、
ワークフローが `cygpath` で組み立てて回収できる。macOS は `mktemp -d` なので、
**パスを知っているのはハーネスだけ**。収集ステップはハーネス終了後に走るから、
その時にはディレクトリごと消えている。

**直し方は「移す」ではなく「コピーを staging する」。** `installtest-common.sh` は
ハーネスの scratch をリポの外に置く理由を明記している(`git status` に出さないため)し、
固定共有パスにするとローカルの並行実行が衝突する。`cleanup()` の `rm -rf` の直前で
`$RUNNER_TEMP` へコピーすれば、CI だけが変わり開発者の Mac の挙動は変わらない。
`$RUNNER_TEMP` staging は `installtest-windows.ps1` の SAC レポートが既に使っている前例。

### 3. 「job log に出しているから良い」は収集しない理由にならない

`engine-only` の収集が linux 限定だった根拠はコメントにこう書かれていた —
「他の 2 つは mktemp に置いていて、失敗パスで**関連ログを job log に tail している**」。

job log は artifact ではない。**期限で消える / 差分が取れない / `tail -40` はファイルではない。**
しかも macOS についてはそもそも偽で、tail する前にトラップがファイルを消していた。

### 4. 警告は「常に鳴る」と読まれなくなる

#1157 で `collect-engine-diag.sh` に「engine ログが 1 本も無い」警告を足した。
これは #1156(中身の無い artifact が成功に見える)を捕まえるためのもので、正しい。

ところが `installtest.yml` の 3 レグは**どれもエンジンを入れない**(#138 以降
install.sh はエンジンを入れない)。そのまま呼ぶと、**失敗のたびに必ず鳴る警告**になり、
本来の意味を失う。呼び出し側が `EXPECT_ENGINE=0` で黙らせられるようにした。

**自分が入れたガードが、次の呼び出し元で嘘になる**という型。ガードを足すときは、
「これから増える呼び出し元でもこの前提は真か」を見る。

### 5. artifact 名には `run_attempt` を入れる

`run_id` だと**同じ run の再実行**で前回の artifact と名前が衝突し、upload が落ちる。
リポの diag 系はすべて `run_attempt` で揃っていたが、`sac-signing-audit` と
`catalog-radar` だけ抜けていた。今日 #1160 で実際に「失敗ジョブの再実行」をしたので、
これは机上の話ではない。
