# ローカルエンジンはプレフィックスをキャッシュする — 遅いのは初回ターンだけ (20260819 21:30)

## Issue

waired-agent#838 は「コーディングエージェントは毎ターン全コンテキストの
prefill を払っている」という前提で起票されていた。実測すると前提が違った。

実際の Claude Code を intercept (`:9472`) の手前に置いたログプロキシ経由で
走らせて採った値:

| | TTFT |
|---|---|
| セッションの1ターン目 | 14.15 秒 |
| 2ターン目 | 0.38 秒 |
| 3ターン目 | 0.40 秒 |

`system` (6,346 文字) と `tools` (54 本 / 110,738 文字) はターンを跨いで
**バイト一致**しており、会話は末尾に追記されるだけ。変換層はプレフィックスを
壊しておらず、エンジンは共通プレフィックスを再利用している。

これは 2026-07-01 の裁定
(`system` ブロック配列の平坦化) が `cache_control` を捨てる理由として書いた
「ローカルエンジンはキャッシュしない」と食い違う。日付入りの記録は凍結する
ルールなので、当時の記録はそのままに、現在の挙動をここに残す。`cache_control`
を無視すること自体は今も正しい — ollama も vLLM も共通プレフィックスを自動で
キャッシュし、境界のヒントを受け付けないため。

## Learnings

計測は 3 OS。捕捉した実リクエスト (30,359 トークン) を、waired が叩くのと同じ
OpenAI 互換面に流し直したもの。全ホスト ollama 0.32.13。

| シナリオ | Linux / 24GB dGPU / 35B-A3B | macOS / ユニファイドメモリ / 35B-A3B | Windows / 8GB dGPU / 4B |
|---|---|---|---|
| weights ロード | 6.85 s | 16.25 s | 9.95 s |
| A 冷 (フルプレフィル) | 10.07 s | 41.51 s | 45.27 s |
| A 再送 (ヒット) | 0.48 s | 1.13 s | 3.33 s |
| B (別プロジェクト) | 9.92 s | 41.50 s | 36.94 s |
| B の後に A | 9.84 s | 41.71 s | 36.91 s |
| 90 秒アイドル後に A | 0.51 s | 1.16 s | 4.09 s |
| unload → reload 後に A | 6.82 + 10.07 s | 15.00 + 41.47 s | 10.55 + 36.28 s |

3 OS で共通して言えること:

- **温まったまま生き残る大きなプレフィックスは事実上 1 本**。A → B → A は
  毎回フルプレフィルに戻る。Claude Code の system プロンプトはプロジェクト固有の
  memory ディレクトリのパスを含み、その分岐点が 6,346 文字中 2,789 文字目 =
  ツール定義より手前に来るため、プロジェクトを跨いだ再利用はほぼゼロ。
- **アイドルではキャッシュは死なない**。runner が生きている限り残る。
  `OLLAMA_KEEP_ALIVE` の失効で runner が落ちると、weights ロードと
  フルプレフィルの両方を払い直す。
- 追記だけの継続ターンは、増えた分しか prefill されない。

計測の副産物として、プレフィックス KV キャッシュのヒットは見かけの prefill 速度が
数万〜十数万 tok/s になるので、レート値だけでヒット/ミスを判別できる
(`docs/knowledges/20260807/1450-prompt-token-cost-must-be-measured.md` が
プローブで nonce を使ってこれを意図的に外しているのと同じ現象)。
