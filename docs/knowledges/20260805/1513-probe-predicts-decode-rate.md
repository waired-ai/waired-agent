# インストール時プローブは他モデルの速度を予測できるか (20260805 15:13)

## Issue

waired-agent#496 の**着手前提**。#496 は「推奨を確定する前に ~1 GB のプローブ
モデルを引き、既存のブートベンチ (`cmd/waired-agent/inference_bench.go`) を
そのモデルに対して走らせ、実測レートで推奨する」を decided approach として
いる。ただし issue 自身のコメントが、先に確かめるべき点を挙げている:

> プローブの実測レートが、それを使って選ぶ対象（4B〜35B q4）のレートを
> **予測する**こと。実在するが無関係な量を測るプローブは、置き換える母集団
> 定数より**悪い** — 権威に見えるから。

24 GB 参照ホスト（RTX PRO 4000 Blackwell 24 GB / DDR5 / ollama 0.31.1 /
Linux）に出荷カタログのモデルがほぼ揃っているので、**ダウンロードなしで**
A/B が取れる。

## 方法

`measureOllamaNative` と同一にした。`POST /api/generate`、`stream:false`、
`options: {num_predict: 200, temperature: 0}`、prompt は `benchPrompt`、
レートは `eval_count / eval_duration`。計測外のウォームアップ 8 トークンを
1 回、そのあと 3 サンプルの中央値、spread は `(max-min)/median`。モデル毎に
`keep_alive: 0` でアンロード（24 GB のモデルを `OLLAMA_KEEP_ALIVE` の 1 時間
居座らせないため。#202 の residency の指摘はこの実験にも当てはまる）。

CPU-only レッグは `options.num_gpu = 0`。**効いたことを推測ではなく確認した**:
llama-server の起動行に `-ngl 0`、`/api/ps` の `size_vram == 0`、nvidia-smi が
16 MiB。`CUDA_VISIBLE_DEVICES` はこのホストでは効かない（ollama は Vulkan)。

`b` は `hostfit.ActiveBytesPerToken`（密 = `estimated_weight_gb`、MoE =
それ × `active_params / param_count`）を `proto/catalog/bundled/*.json` から
計算した値。effBW = 実測 tok/s × b。

この計測中に #515 が入り、製品側は完了長をホストに合わせて縮めるように
なった（遅いホストは 200 ではなく `benchProbeTokens = 32` から始める）。
ここでは固定 200 を使っている — 速いホストが今も受け取る長さである。
`inference_bench_sizing.go` 自身が書いているとおり
「`eval_count`/`eval_duration` は純粋なデコードカウンタなので短い run でも
偏りのないレートサンプルになる」ので、この差はレートを動かさない。

## Learnings

### 1. effBW は b に対して平坦ではない — 単純な外挿は成立しない

GPU レッグ（全モデル resident、`offloaded 66/66 layers` 等をログで確認）。
独立に 2 回走らせ、再現性は 0.1〜1.6%（`benchSampleCount` のコメントが想定
する ~8% よりはるかに厳しい）。したがって以下の傾向はノイズではない。

| model | b (GB) | tok/s | effBW (GB/s) |
|---|---|---|---|
| granite4-350m | 0.7000 | 505.1 | 353.6 |
| qwen3.5-0.8b | 1.0000 | 349.6 | 349.6 |
| qwen3.5-2b | 1.9000 | 272.0 | 516.8 |
| qwen3-coder-30b-a3b | 1.9889 | 192.6 | 383.0 |
| qwen2.5-coder-3b | 2.0000 | 219.6 | 439.2 |
| qwen3.6-35b-a3b | 2.2534 | 156.5 | 352.8 |
| qwen3.5-35b-a3b | 2.2629 | 155.0 | 350.7 |
| gpt-oss-20b | 2.4170 | 129.4 | 312.6 |
| qwen3.5-4b | 3.4000 | 144.1 | 490.0 |
| qwen3.5-9b | 6.6000 | 92.4 | 610.0 |
| qwen3.5-27b | 17.0000 | 31.6 | 537.1 |

密モデルだけで effBW は 350 → 610 GB/s、**74〜79% の幅**。`t = b/BW + c` の
最小二乗は **BW = 561〜571 GB/s、c = 0.80〜0.88 ms/token、R² = 0.99**。
つまりカードの実帯域に 1 トークンあたり固定コストが乗る形で、1 GB のモデル
ではその固定コストが支配的になる。1 GB のプローブから外挿すると 9B を
**43% 過小評価**する。

CPU-only レッグ:

| model | b (GB) | tok/s | effBW (GB/s) |
|---|---|---|---|
| granite4-350m | 0.7000 | 56.41 | 39.5 |
| qwen3.5-0.8b | 1.0000 | 41.87 | 41.9 |
| qwen3.5-2b | 1.9000 | 29.29 | 55.7 |
| qwen3-coder-30b-a3b | 1.9889 | 20.27 | 40.3 |
| qwen2.5-coder-3b | 2.0000 | 21.05 | 42.1 |
| qwen3.6-35b-a3b | 2.2534 | 15.93 | 35.9 |
| qwen3.5-35b-a3b | 2.2629 | 15.84 | 35.9 |
| gpt-oss-20b | 2.4170 | 10.95 | 26.5 |
| qwen3.5-4b | 3.4000 | 13.59 | 46.2 |
| qwen3.5-9b | 6.6000 | 7.56 | 49.9 |
| qwen3.5-27b | 17.0000 | 2.56 | 43.5 |

CPU 側の幅は 55%。向き自体は GPU と同じ（小さいモデルほどバイトあたり遅い）
だが、**単調ではなく b ≈ 1.9 で頭打ちになる**。そのため同じ `t = b/BW + c`
を当てると切片が**負**になり、小さい側を +26% 過大評価する（granite:
フィット 71.0 / 実測 56.41）。R² は 0.99 と出るが、これは b = 17 の 1 点が
フィットを支配しているためで、モデルが CPU ホストを記述できている証拠では
ない。GPU 側は c > 0（0.80〜0.88 ms/token）で素直に当たる。
**片方に合わせた補正はもう片方で外れる。**

### 2. しかし推奨が消費するのは速度ではなく「フロアを超えるか」の二値

`OllamaRecommend` が読むのは `Estimate.MeetsSpeedFloor`、すなわち
`hostfit.DecodeFloorTokps = 20` を超えるかという二値だけ。**点予測ではなく
分類器として採点し直すと結果が反転する。**

DecodeFloorTokps = 20 に対する正答数（実測を正解とする）:

| 予測器 | CPU (11) | GPU (11) |
|---|---|---|
| 定数 60（`BandwidthSystemRAMGBs`） | 8/11 | 8/11 |
| probe: granite4-350m | 9/11 | 11/11 |
| **probe: qwen3.5-0.8b** | **11/11** | **11/11** |

点予測は最大 43% ずれるのに、**qwen3.5-0.8b プローブは 22/22 全問正解**。
一方 **定数 60 の CPU 側 3 誤りはすべて MoE の false-pass** —
qwen3.6-35b-a3b（予測 26.6 / 実測 15.9）、qwen3.5-35b-a3b（26.5 / 15.8）、
gpt-oss-20b（24.8 / 10.9）。#496 が報告している症状そのものである。

### 3. プローブモデルは qwen3.5-0.8b。granite4-350m ではない

issue のコメントが open にしていた点は、計測で決まった。granite4-350m の
CPU 側 2 誤りはどちらも false-block で、フロアのすぐ下に置いてしまう:
qwen3-coder-30b-a3b（予測 19.9 / 実測 20.3）、qwen2.5-coder-3b（19.7 / 21.1）。
ダウンロードは 30% 少ないが、**実際に効く帯域で判定を落とす**。

### 4. プローブが安全なのは 20 フロアまで。60 フロアには使えない

`router.CodingAgentSelectionFloorTokps = 60` で同じ採点をすると、GPU 側で
どちらのプローブも **qwen3.5-9b を false-block** する（予測 53.0 / 実測 92.4）。
1 GB プローブの過小評価がちょうど 60 をまたぐため。プローブは
`DecodeFloorTokps` のゲートに限定し、60 フロア（#133 の軽量化/アップグレード
提案が使う側）には配線してはいけない。

### 5. MoE は同じアクティブバイトの密モデルより遅い — 外挿なしの直接 A/B

`qwen2.5-coder-3b`（密、b = 2.0000）が、出荷 MoE 3 種のアクティブバイトと
ほぼ同じという偶然を使うと、ルーフラインを介さない直接比較ができる。

| MoE | b (GB) | GPU で遅い | CPU で遅い |
|---|---|---|---|
| qwen3-coder-30b-a3b | 1.9889 | 12.8% | 4.2% |
| qwen3.6-35b-a3b | 2.2534 | 19.7% | 14.7% |
| gpt-oss-20b (MXFP4) | 2.4170 | 28.8% | 37.2% |

**`ActiveBytesPerToken` は MoE の速度を系統的に過大評価する。** これが定数 60
が MoE で false-pass する理由。ただし 4〜37% と幅が広く、4 点しかないので、
**単一の補正係数を置くには根拠が足りない**（下の 6 も参照）。

### 6. `ActiveBytesPerToken` は密モデル同士でも ±20% ずれる

`qwen3.5-2b`（b = 1.9、GPU 272.0 tok/s）と `qwen2.5-coder-3b`（b = 2.0、
219.6 tok/s）は b が 5% しか違わないのに **24% 違う**。実ファイルサイズは
1.95 GB と 1.93 GB でほぼ同一なので、差は世代・層数・ヘッド構成であって
重みバイト数ではない。この散らばりが、この方式全体の精度の上限を決める。

### 7. 免除を外すだけでは #496 の症状は直らない

まず前提を一つ正す。「CPU-only では recommend ゲートが stand down する」は
**誤り**だった。実コードで確認すると 64 GB CPU-only ホストでは
`ranked=10, recommended=10` — ゲートは空にならない。理由は
`internal/router/model_picker.go:265-275` がすでに書いている:

> **There is no longer a speed pass.** The #229 roofline is still computed and
> still reported ... but it no longer EXCLUDES, on any class. ... And it prices
> decode only, while a coding agent's work is ~21:1 prefill-heavy. Speed becomes
> a recommendation input again when it is MEASURED rather than assumed (#466).

つまり速度はどのクラスでも除外していない（`hostfit.OllamaRecommend` の
`ClassUnified` アームだけは、チップ表にある実機の公表ピークを上界として
`ReasonTooSlow` を出せる — #251 の別ルール）。速度推定値は計算され報告されて
いて、**使われていないだけ**である。同じコメントが定数の当てにならなさも
記録している: 「同じ数字が 19.96 tok/s のホストを除外し 17.65 tok/s の
ホストを通した — 速いほうが拒否された」。

64 GB CPU-only ホストに出荷カタログ全体を当てた結果:

| 速度モデル | 両フロア通過数 | 最上位の選定 |
|---|---|---|
| 定数 60（免除を外すだけ） | 7 | qwen3.6-35b-a3b (tier 90) |
| プローブ (qwen3.5-0.8b) | 3 | qwen3-coder-next-80b-a3b (tier 86) |
| 2 点スロープ | 6 | qwen3.6-35b-a3b (tier 90) |

プローブは tier 90 / 89 / 73 / 60 の MoE を落とすが、**tier 86 の
qwen3-coder-next-80b-a3b は残る**（b = 1.998 なので予測 21.0 tok/s）。
そしてこれは的外れな予測ではない: 同じ ~2 GB アクティブの
qwen3-coder-30b-a3b は CPU で実測 20.27 tok/s、密の 3B が 21.05 tok/s —
**デコードに関する限りルーフラインはほぼ正しい**。

### 8. プレフィルを測ると、#496 の前提が逆になる

ベンチのプロンプトは 14 トークンなので、そこでの `prompt_eval_*` は固定
オーバーヘッドに支配されていて使えない（granite が GPU で 20,314 tok/s と
出る）。5.8k トークン・`num_predict: 1` で測り直した。**プロンプト先頭には
毎回ノンスを置く** — ollama は共有プレフィックスで KV をキャッシュするので、
同じプロンプトの 2 回目は `prompt_eval_count` を満額返しつつ所要時間ほぼ 0
（実測 697,222 tok/s）になり、黙って嘘の値が入る。

1 ターンを `P/prefill + (P/21)/decode` で価格付けした CPU-only:

| model | tier | 総params | prefill | decode | prefill 秒 | decode 秒 | 1ターン |
|---|---|---|---|---|---|---|---|
| qwen2.5-coder-3b (密) | 30 | 3B | 350.6 | 21.05 | 16.6 | 13.1 | **29.7 s** |
| qwen3.6-35b-a3b (MoE) | 89 | 35B | 212.3 | 15.93 | 27.3 | 17.3 | **44.6 s** |
| qwen3-coder-30b-a3b (MoE) | 65 | 30B | 181.2 | 20.27 | 32.0 | 13.6 | **45.6 s** |
| qwen3.5-9b (密) | 52 | 9B | 157.6 | 7.56 | 36.7 | 36.5 | **73.2 s** |
| qwen3.5-27b (密) | 69 | 27B | 46.6 | 2.56 | 124.2 | 107.7 | **232.0 s** |

**相対順位と絶対的な使用可能性は別の問いで、答えが違う。**

*相対*には、tier 89 の MoE は CPU-only ホストの選択肢の中で最高品質かつ 2 番目
に速い — tier 52 の密モデルに品質でも 28 秒でも勝ち、tier 69 には 5 倍以上速い。
*絶対*には、**どれも使い物になっていない**: 15.93 tok/s は
`DecodeFloorTokps = 20`（「そもそもダウンロードする価値があるか」）を下回り、
`CodingAgentSelectionFloorTokps = 60`（「作業できる速さか」）には遠い。
「最もマシ」であって「使える」ではない。

したがって #496 の問題意識は向きとしては正しい。ただし理由が違う —
*より小さいモデルの方が良い* からではなく、**そのホストではどれも十分でない**
のに tier 89 を平然と推奨しているから。

プレフィルは CPU ターンの 50〜70%、GPU ターンでも 32〜52% を占める。そして
**プレフィルはアクティブでも総パラメータでもスケールしない**: GPU で
30B-A3B は 4,204 tok/s。総パラメータでスケールするなら 3B 密の 9,614 から
~960 のはずで、アクティブでスケールするなら 9,614 のはず。実測はその中間で、
**9B 密の 3,936 の隣に座る**（プレフィルはバッチ処理なので FLOPs はアクティブ、
重み読み出しはバッチで償却される）。正しい言い方は「MoE のプレフィルは同じ
アクティブサイズの密モデルの 2〜3 倍遅い」。これが `ActiveBytesPerToken` に
構造的に見えない項であり、#466 の領分である。

### 9. デコードフロアだけを当てると、より大きいモデルが選ばれる

7 のプローブ列で除外されるのは qwen3.6-35b-a3b (tier 90/89、実測 15.9)、
qwen3.5-35b-a3b (73、15.8)、gpt-oss-20b (60、10.95)。両フロアを超えて残るのは
qwen3-coder-next-80b-a3b (86、予測 21.0、**未計測**)、qwen3-coder-30b-a3b
(65、実測 20.27)、qwen2.5-coder-3b (30、実測 21.05 — #522 で退役予定)。

つまりローカル推論はオフにならず、**選定が 24 GB の 35B-A3B から 45 GB の
80B-A3B に変わる**。デコードフロアを満たすために、より大きいダウンロードを
させることになる。80B の 21.0 は予測値で、MoE の実測ずれ幅（4〜37%）を
当てはめれば 20 を割りうる。

**デコード tok/s 単体では正しい判断ができない。** 効く基準は 1 ターンの
所要時間（プレフィル込み）であり、それは #466 が持つ。

### 10. カード付きホストは損をしていない

本文の表は 16 GB カード機の tier 52 を「低すぎる」側に置いているが、
qwen3.5-9b は 16 GB カードに完全常駐する。24 GB カードでの実測は decode
92.4 tok/s / prefill 3,936 で、**1 ターン 4.5 秒** — CPU-only 機の tier 89
44.6 秒に対して桁違いに良い体験である。カード機は自分が実際に速く動かせる
モデルを与えられている。

残る正当な問いはもっと狭い: *16 GB カード機にとって、常駐する 9B より
スピルする 24 GB MoE の方が本当に良いのか*。これは未計測（下記）。

### 11. 深さを入れると数字が変わり、結論も変わる

上はすべて浅い計測（プロンプト 14 トークン、生成 200）。実際のコーディング
セッションの文脈長（ここでは 21,078 トークン）で測り直すと:

| model | leg | prefill | decode | 浅い decode からの低下 |
|---|---|---|---|---|
| qwen3.6-35b-a3b | cpu | 155.8 | 10.92 | −31% |
| qwen2.5-coder-3b | cpu | 205.2 | 12.08 | −43% |
| qwen3.5-2b | cpu | 470.4 | 22.31 | −24% |
| qwen3.5-0.8b | cpu | 675.2 | 28.44 | −32% |
| granite4-350m | cpu | 658.9 | 22.42 | −60% |
| qwen3.5-9b | gpu | 3,689.3 | 82.94 | −10% |
| qwen3.5-0.8b | gpu | 19,975.3 | 293.2 | −16% |

**ブートベンチの浅い計測は、実セッションのデコードレートを CPU で 24〜60%、
GPU で 10〜16% 過大評価する。** 1 ターン（`P/prefill + (P/21)/decode`）:

| ホスト | model | tier | 1ターン |
|---|---|---|---|
| CPU-only | qwen3.6-35b-a3b（現在の選定） | 89 | **227 s** |
| CPU-only | qwen2.5-coder-3b（最小の密） | 30 | **186 s** |
| 24 GB カード | qwen3.5-9b | 52 | **17.8 s** |

CPU-only はカード機の 10〜13 倍遅く、**モデルを小さくしても救われない**
（227 → 186 s）。これはモデル選定の問題ではない。

なお 24 GB カードで qwen3.6-35b-a3b に 22k 窓を要求すると CUDA OOM するが、
これは製品の欠陥ではない: 実コードで確認すると同モデルは同カードで既に
`recommend=false (weights_spill)`（重み 24,773 MB > 予算 24,467 MB）で、
選定は qwen3.6-27b (tier 70, spill 0.00) になる。手で load させただけ。

### 12. 足切りが目的なら、外挿は要らない

プローブ自身の 1 ターン所要時間を見ればよい:

| ホスト | qwen3.5-0.8b (1 GB) の 1 ターン | 計測コスト |
|---|---|---|
| CPU-only | **66.5 s** | 39.9 s |
| 24 GB カード | **4.5 s** | 4.3 s |

**15 倍差**。ルーフラインも `ActiveBytesPerToken` も MoE 補正も使っていない、
実測値そのもの。論理は「カタログ最小級の 1 GB モデルですら 21k で 1 ターン
66 秒かかる機械は、それより大きい何を入れても改善しない」で、実際 11 の表が
そうなっている。

閾値を置くため反復した（各 run は `keep_alive: 0` で毎回コールドロード。
ロード時間は 1.6 s / 2.3 s なので 1 ターンにはほぼ効かない）:

| leg | 各 run の 1 ターン | 中央値 | 幅 |
|---|---|---|---|
| CPU-only | 65.3 / 65.9 / 66.6 / **80.4** / 67.5 | **66.6 s** | 22.7% |
| 24 GB カード | 4.5 / 4.5 / 4.6 | **4.5 s** | 2.2% |

**アイドル時の再現性は ±2%。** 外れ値の 80.4 s は 1 本だけで、別セッションの
`terraform` が同時に走っていた（decode が 28.5 → 20.9 に落ちている）。実運用の
変動は「静かなら ±2%、競合すれば +21%」という形になるので、閾値はこの幅を
吸収できる位置に置く必要がある。決定は 45 秒
（`docs/decisions/20260805/1620-host-cutoff-is-a-measured-probe.md`）。

外挿の方は採点した結果**信用できない**。qwen3.5-0.8b（21k 実測）からの
1 ターン予測誤差:

| ターゲット | 実測 | 予測 | 誤差 |
|---|---|---|---|
| qwen2.5-coder-3b (cpu) | 186.0 s | 187.8 s | +1% |
| qwen3.6-35b-a3b (cpu) | 227.2 s | 208.3 s | −8% |
| qwen3.5-2b (cpu) | 89.8 s | 145.1 s | **+62%** |
| granite4-350m (cpu) | 76.8 s | 38.4 s | **−50%** |
| qwen3.5-9b (**gpu**) | 17.8 s | 34.5 s | **+93%** |

最後の行が危ない: 1 GB のモデルは速いカードの上ではトークン毎の固定コスト
（1 の c ≈ 0.8 ms）に支配されるので、プローブは GPU のレートを約 2 倍
過小評価する。**30 秒の閾値を置くと健全な GPU 機を誤って切る。**
プローブ自身のターンを見る方式にはこの問題がない。

## 未計測 / 次に確かめること

- **80B-A3B の実測**。プローブ適用後に最上位で残る tier 86 は、このホストに
  キャッシュがなく（45 GB）予測のまま（両フロアを超えて残るのは
  80b-a3b / qwen3-coder-30b-a3b / qwen2.5-coder-3b の 3 件）。MoE のずれ幅
  （4〜37%）を考えると 20 を割る可能性は十分ある。
- **さらに深い文脈**。11 は 21k での計測。プレフィル速度は文脈長とともに
  落ち続けるので、200k を宣言するセッションの 1 ターンは上の表より悪い。
  外挿はしていない。
- **スピルした MoE**。16 GB カード + 64 GB RAM に 24 GB の MoE を載せた場合の
  レートは未計測。`num_gpu: N` で層数を絞れば再現できる。
- **45〜25 秒の帯**。12 の反復で両端は固まったが、その間は空白のまま。
  該当するのは (a) 多チャネルのサーバ CPU — このワークロードは CPU では帯域
  律速で、実効帯域はこの箱（デュアルチャネル DDR5）で 40〜56 GB/s。8〜12ch の
  EPYC/Xeon なら 4〜8 倍あり得るので、CPU-only でも 10〜20 秒で**通過する**
  はず（正しい挙動だが未確認）。(b) 弱い dGPU / iGPU — プローブは 1 GB なので
  2 GB のカードにも全常駐し、カード自体の素の速さがそのまま出る。この帯の
  実測が無い。
- 別ホストでの再現。2 の分類の何件かはフロアから数 % の位置にあるので、
  1 ホストの 22/22 は「定数より良い」の証拠であって、一般化の証明ではない。
