# 何も検査しないまま通るテストとガードの型 (20260921 21:00)

## Issue

テストやガードが通っていることは、それが欠陥を検出できる証拠にならない。
waired-agent で実際に起きた「通っているが何も検査していなかった」型を、
確かめ方と一緒に 1 か所にまとめる。タイミングと並行に固有の型は
`docs/knowledges/20260921/2110-timing-and-concurrency-test-shapes.md`、
手元の Linux で通り他の OS で落ちる型は
`docs/knowledges/20260921/2120-green-on-linux-red-on-other-os.md` に分けた。

セッションのメモリに在った知見を、オーナーの指示(2026-09-21、
waired-ai/waired-ai#12)でリポジトリへ移した。

## Learnings

### 1. 直しを一時的に戻して、落ちるテストの本数と名前を見る

いつ読むか: 新しいテストを書いたとき。順序・優先順位・フォールバックを固定する
テストは戻す変更が 1 行で済むので、毎回やる価値がある。

新しいテストが通ることは、そのテストが欠陥を捕まえる証拠にならない。欠陥は
「ある状態でだけ」出る。フィクスチャがその状態の隣に居ると、テストは通り、
実装のどの行を消しても通り続ける。mutation testing の要領で、実装の該当箇所を
一時的に元へ戻し(以下「変異」)、落ちる本数と名前を見る。

```sh
test -z "$(git status --porcelain)" || { echo "先に commit(WIP でよい)"; exit 1; }
cp <file> "$SCRATCH/<file>.bak"      # 変異の前に 1 回
sed -i 's/…/…/' <file>               # 変異
go test ./… 2>&1 | tee out.txt       # `build failed` が無いかを先に見る
cp "$SCRATCH/<file>.bak" <file>      # 変異ごとに復元し、最後に「復元して通る」を確認
```

- 復元に `git checkout -- <file>` を使うと、直しが未コミットのとき変異と一緒に
  直しも消える(2026-09 に 5 回起きた。症状は「2 本目以降の変異が全部
  `build failed`」や「復元したのに通らない」)。先に commit し、復元は退避した
  コピーから行う。
- 変異ごとに復元する。挟まないと、2 本目以降は前の変異が乗った状態を試している。
- ループで回している間は同じ worktree を触らない。最後の復元が別の編集を消す。
- ビルド失敗は「変異を入れても落ちなかった」に見える。`--- FAIL` の行数だけを
  数えると、import が未使用になってパッケージごとビルドできなかった変異が 0 本に
  見える。条件を潰す変異は `if false && <元の式>` の形にして、元の式のシンボルを
  生かす。
- 文字列置換の変異は、一致しなければ何も変えずに終わる。変異が実際に当たったかを
  `git diff` で見る。

落ちたのが 0 本だったときは、次の順に原因を引く。

1. フィクスチャが欠陥の状態を再現していない。「この欠陥が出るとき本番の状態は
   どうなっているか」を製品コードから引き、フィクスチャをそちらへ寄せる
   (例: 共有を off にしたホストでは、保持していた割り当てが全部解放されて対応表が
   空になっている。ピアを 1 台置いたフィクスチャは、報告された状態を再現して
   いなかった)。比較の両辺が取り得る値(空 / 別の既存 / 同じ)を 1 行ずつ置く。
2. 配線を試していない。射影と導出の純関数に表テストが揃っていても、その 2 つを
   繋ぐ 1 行(スナップショットへの append)を消して 0 本だったことがある。
   「製品がその関数を呼ぶ経路」を 1 本通すテストを足す。
3. その変更が本番で到達不能。同じ PR の別の直しで、その枝に入る状態がもう
   起きない。落ちるフィクスチャは作れるが、作ると本番で通らない枝にテストが付く。
   変更を消し、その枝が要らない理由をコメントに残す。フィクスチャを疑う前に
   「この変更が効く状態は本番で起き得るか」を先に引く。
4. テストが対象を呼んでいない。テスト本体に製品と同じ式
   (`errors.Is(c.err, router.ErrAllPeersOverloaded)` など)がもう一度書かれて
   いたら、それは標準ライブラリを検査している。判定が 1 行のインラインだと呼べる
   先が無いのでこの形になる。判定を関数に出してテストから呼ぶ(CLAUDE.md
   §Test discipline「Put the seam below the behaviour under test」)。
5. 想定より少ない本数しか落ちないときも同じ。残りの行は別の理由で通っている。
   その行を落とすか、形だけを固定している旨をコメントに書く。

5 の実例(waired-agent#995、2026-08-22): 「バックアップが何本残ったか」を数える
テストを 9 本書き、全部通してから修正を戻して走らせたら、4 本しか落ちなかった。
中心の `TestApply_RepeatedApplyLeavesOneBackup` は通ってしまっていた。バックアップ名が
`<path>.waired-bak-<unix 秒>` で、テストの Apply が全部同じ秒に走るので同じ
ファイル名に落ち、コードが何本作ろうと結果は 1 本だった。時刻の差し替え口
(`backupClock`)を入れて 1 本ずつ別の秒に置いたら 8 本落ちた。落ちない本数が
あったら「別の観点を見ている」ではなく「測っていない」を先に疑う。数を数える
アサートは、数える対象の名前が衝突しないことを先に保証する。

手元の Linux では変異を入れても落ちない型もある(2 点の時刻の順序。
`docs/knowledges/20260912/1400-clock-resolution-is-an-os-property.md`)。

### 2. 条件を絞るたびに、その経路を通るテストが減る

いつ読むか: 副作用を起こす条件(トリガ)を狭める変更を入れるとき。

waired-agent#783 の作業で、再ベンチマークのトリガ条件を 3 回絞った結果、どの
テストもその呼び出しに到達しなくなった。その状態で「detach をやめてブロックする」
案を書いたら、手元の全スイートが通った。実際には `endPull` が `runPullJob` の
defer で、`engineIsQuiet` は pull の進行中 false を返すため、本番ではデッドロック
する変更だった。全部通ったのは「安全」ではなく「誰も通っていない」の意味だった。
次のリファクタで同じ穴が再発したときも、同じく全部通る。

- トリガを絞ったら、経路を通ることを確かめるテストを 1 本足す。副作用の入口
  (関数呼び出し・チャネル送信)が実際に起きたことを見る。
- そのテストが何かを検査していることを実測する。トリガを一時的に外してそのテストが
  落ちることを確認し、復元する(§1)。
- コメントで理由を書くのは必要だが、それだけでは足りない。コメントは CI で検査
  されず、次に疑う人はその場で変更して全部通るのを見る。
- 同名で違う問いに答える述語を 2 つ置くときは、差をコメントに書く
  (例: `benchDescribes` は既存の結果を「使ってよいか」に答え、ラベルの無い結果は
  使う。再測定の要否に答える側は、ラベルの無い結果を測り直す)。書かないと、次の
  人が片方に寄せる。

### 3. 起きなかったことが、起こす必要が無かったことと同じに見える

いつ読むか: 新しいアサートを足したとき。スキップや何もしない分岐を書くとき。

2026-08-27 の 1 日に 3 つのセッションで 4 回起き、その後も出ている形。

- CI のアサートが `skip` に落ちて通る(`scripts/dev/installtest-run.sh`、
  `WAIRED_NO_TRAY=1` でパッケージが無い)。サマリの
  `47 passed, 0 failed, 2 skipped` は何も言わない。
- Windows の更新で、トレイの再起動が無言で行われない。`Get-ConsoleUser` は切断中の
  セッションで空を返して `skip:no-console-user` に落ちるが、その分岐はログを
  出さない。
- `ViewAt` がパース失敗を握り潰し、BOM 付きの managed settings が「ファイルはあるが
  未設定」と同じに見える(waired-agent#1067)。
- TUI テストの待ち条件 `>` が `C:\>` に一致し、Claude Code が起動しないまま PASS。
- `scripts/ci/i18n-pair-guard.sh` はコミット済みの差分しか見ない。未コミットのまま
  回すと `no English docs page touched; nothing to check` で通る。コミットしてから
  回す。

対処:

- 新規アサートを足したら、通ったことではなく、ジョブログのアサート行を逐語で確認
  する(`gh api --allow-escape-sequences repos/<o>/<r>/actions/jobs/<id>/logs`)。
  `N passed, 0 failed` は自分のアサートが走った証拠にならない。
- スキップにはアサートの前提を用意させる。`skip` で立ち去らず前提を満たしに行き、
  満たせないなら `bad` で落とす(`installtest-run.sh` の `it_ensure_tray_pkg` の形)。
  ジョブ全体の既定を変えるのは、他のアサートの足場を動かすので最後の手段。
- ユーザーの見え方が変わるスキップは 1 行出す。「アプリを再起動しなかった」は、
  ユーザーには「更新したのに古いまま」に見える。
- 失敗と不在を、呼び出し元が区別できる形で返す。BOM を剥がすような直しは今日の
  引き金を外すだけで、次の引き金は外れない。
- 画面のテキストや存在チェックで「起きた」を判定しない。ログ・PID・プロセスの
  開始時刻など、起きなければ現れない証拠を見る。

### 4. フェイクとフィクスチャが置き換えている場所の欠陥は見えない

いつ読むか: 「その面のテストは充実している」のに実機で欠陥が出たとき。オプショナルな
インタフェースや deps 構造体の既定値を読むコードを書いたとき。

「その面のテストは充実している」は「その面が正しい」の根拠にならない。seam が
どこに引かれているかで、何が書けないかが決まる。面の欠陥を疑うときは、まず
フェイクとフィクスチャが何を置き換え、何を埋めているかを読む(原則は CLAUDE.md
§Test discipline「A fake placed at the defect boundary means the subject never
runs」)。

**4a. フェイクが対象の関数を丸ごと差し替えている。** セットアップウィザードの
エンジン行の表テストは `fakeSetupProvider` を通り、そのフェイクは
`setupEngineHealth` を丸ごと差し替えてスクリプト値を返す。表は「latched=true なら
こう描く」しか見ておらず、「本物が latched を返し損ねる」は書けない
(waired-agent#1093。表は全部通り、実機は正常と表示していた)。

- 修正のテストは本物のアダプタを使う側に置く(この件は
  `cmd/waired-agent/inference_startfail_test.go`)。
- 表テストが 1 本も反転しないのは「安全な変更だから」ではなく「表がその事実を
  見ていないから」のことがある。PR 本文で書き分ける。

**4b. フェイクがそのメソッドを持っているので miss 側を通らない。** オプショナルな
インタフェースアサーション
(`if fl, ok := a.(interface{ FailureLatched() bool }); ok`)は fail-open。経緯と
塞ぎ方 2 つ(実物へのコンパイル時アサート、本当に実装していないフェイク)は
`docs/knowledges/20260830/0105-fail-open-guards-need-a-recoverability-line.md` §4 に
在る。そこに無い補足:

- コンパイル時アサートは `var _ interface{ … } = (*T)(nil)` と書く。lint が名前付きの
  変数を `unused` で弾く。OS 限定の型はタグ付きファイル側に置く。
- miss 側のフェイクには、「そのフェイクが当のメソッドを実装していないこと」の前提
  アサートを添える。後からメソッドが足されると、miss 行が黙って hit 行に変わる。

**4c. フィクスチャが既定値を注入するので、nil の経路に届かない。** deps 構造体の
既定値を「使う関数の先頭で埋める」形にすると、同じ deps を先に読む別の関数が nil を
踏む(waired-ai/waired#1357 の作業、2026-09-14: `BenchDeps.Now` を
`RunBootBenchmark` の先頭で埋めていたが、ループが先に `awaitServingIdle` へ渡して
daemon が panic し、サービスが再起動した。フィクスチャは全部 `Now` を注入していたので
全部通っていた。実機のログで見つかった)。

- 既定は deps を組み立てる本番の builder で埋める。deps を受ける補助関数は、nil の
  関数フィールドを自前で既定に倒す。
- テストに、本番の builder が作る deps のまま(注入なし)で通る経路を 1 本置く。

### 5. 何でも受ける偽サーバは、ワイヤの文法違反を検出できない

いつ読むか: HTTP の偽サーバや `httptest.ResponseRecorder` でワイヤの値・応答の枠を
固定するテストを書くとき。

`/api/generate` のフェイクがどんな body でも受けて `{"done":true}` を返すので、テスト
5 本が「実物の ollama が HTTP 400 を返す値」をリテラルで正解として固定していた
(waired-agent#927)。中でも「warm が `keep_alive` を明示的に送ること」を検証する
テストが、実物が拒否する値を正解にしていた。

`ResolveKeepAlive(0)` の `"-1"` は環境変数 `OLLAMA_KEEP_ALIVE` では正しく、
リクエストごとの `keep_alive` では単位が無くて `time.ParseDuration` が拒否する。
同じ値を文法の違う 2 か所に使っていた。`"0"` は単位なしでも parse できるので
unload の経路だけが偶然動き、形が隠れていた。結果、既定(無期限)のホストでは
warm が毎回 400 で失敗していた。全テストは通ったまま。

- リテラルでなく性質をアサートする。この件なら「`time.ParseDuration` が通り、
  無期限なら負」。リテラルの固定は、壊れた値を正解として固定することになる。
- フェイクを書くときは「何を拒否するか」を決める。全部受けるフェイクは「呼ばれたか」
  しか検証できない。値の妥当性を見たいなら、実物と同じ拒否を実装する。
- 同じ値を文法の違う 2 か所に流さない。位置が 2 つなら描画関数も 2 つ。隣に置いて
  コメントで対にする(片方だけ直ると再発する)。
- 実物に 1 回でも投げて、綴りごとの応答の表を採る。この件は
  `"-1"`→400 / `-1`→200 / `"-1s"`→200 を採ったことで即座に確定した。

**同じ形の 2 つ目: `httptest.ResponseRecorder` はワイヤの枠を持っていない**
(waired-agent#1314、2026-09-12)。レコーダは `WriteHeader` を 1 回しか覚えず、
`WriteHeader(100)` を最終ステータスとして記録して以降の 200 を捨てる。
`Content-Length` の有無で chunked になるかも、フレームが 1 本ずつ届くかも、終端
チャンクを書かずに閉じたかも、レコーダの `Body` には現れない。「早期に 1 バイト
出す」「本文を分割して届ける」「途中で切る」を主張するテストは、レコーダで書くと
全部通っても何も言っていない。

- 応答の枠(ステータス行の個数、chunked、終端、接続の切り方)を主張するテストは
  `httptest.NewServer` と実物の `http.Client` で書き、本文は `io.ReadAll` のエラー
  まで見る(終端されていない応答は `unexpected EOF` になる)。
- レコーダで足りるのは「本文に何が入ったか」だけ。

### 6. デコード用の JSON フィクスチャは、書いた日のワイヤ形のまま残る

いつ読むか: ワイヤをデコードするテストを触るとき。

新しいフィールドが増えてもフィクスチャは追随しないので、テストは古い互換経路だけを
回し続け、出荷中の全ホストが通る枝を一度も通らないまま全部通る。

実例(waired-agent#862): `TestConfirmModelFitsForPull` の unfit フィクスチャに
`fit` ブロックが無かった。`fit` が nil なのは waired-agent#836 以前の agent の
ワイヤ形。pull ゲート本体のテストは、現行の daemon が毎回送る `fit.reason` の枝を
一度も評価していなかった。#862 の修正でその枝を分岐させたとき、既存テストは 1 本も
落ちなかった。落ちるべきものが最初から通っていなかったから。

- フィクスチャが現行の実サーバの応答の形かを確認する。ポインタ型のフィールドが
  省略されているのは「省略できる」ではなく「旧ワイヤ形を試験している」の合図。
- 現行形のフィクスチャを足し、互換経路は互換経路として別に残す。互換経路のテストは
  価値があるが、それが唯一の経路になっていると逆向きに働く。
- 実サーバの応答を 1 回採って比べるのが速い。

### 7. httptest のリスナは、そのテストだけのものではない

いつ読むか: `httptest` のサーバで「この要求は来ないはず」(不在アサート)や
「3 回のはず」(計数アサート)を書くとき。それがフレークしたとき。

`httptest` はループバックのエフェメラルポートに bind する。テストバイナリ内の
全ゴルーチンから届くうえ、閉じた後にカーネルが同じポートを後続のフィクスチャに
再発行し得る。前のテストが残したゴルーチンが、後のテストのサーバに当たる。届いた
ものを全部数える・記録するフィクスチャは、被験体でなくプロセス全体を観測している。
`unit tests (darwin, seeded host)` は `-count=2` なので、1 プロセスに各フィクスチャが
2 世代同居する。waired-agent#932 / #933 / #1122 / #1008 がこの型で、どれも被験体が
その要求を出せないことは証明でき、要求の出所は特定できなかった。mock が他のテストの
要求を「製品の署名の欠陥」として報告していた例もある。

- 出所を特定する必要はない。フィクスチャが自分の出すトラフィックに印を付け、印付き
  だけを数え、それ以外を別枠で記録して失敗メッセージに出す。
- 印はリスナを立てる前に採る。後から代入するとハンドラのゴルーチンとのデータ競合に
  なり、`-race` が落とす。
- 既存の計数アサートは壊さない。記録は全件のまま残し、印付きだけを返すメソッドを
  別に足す。
- 数えるハンドラは mux で、被験体が実際に POST するパスに載せる
  (`/v1/devices/<id>/node-key/rotate`、`/v1/devices/self/setup-progress`、
  `/v1/chat/completions`)。素の `http.HandlerFunc` で数えているフィクスチャは、
  全部この穴を持つ。
- `http.DefaultClient` の共有プールも同じ穴の半分。アイドル接続は `host:port` の
  キーで全フィクスチャに共有され、`bytes.Reader` から作った POST は `GetBody` 付きで
  net/http が透過的に再送する。フィクスチャごとに `Transport` を Clone した専用の
  クライアントを渡す(`internal/gateway` は 1 バイナリで httptest を 60 個以上開く)。
  `httptest.Server.Client()` は共有の 1 個を返すので、印を付けると全消費者に効く。
- seam は大抵もう在る: `controlclient.Client.HTTP`(公開フィールド)、
  `nodeKeyRotatorConfig.HTTPClient`、`gateway.Deps.HTTPClient`。製品の変更は要らない。
- 何も通さないフィルタは、不在アサートを永久に通す。「印無しは弾かれる」と「印付きは
  通る」の両方を固定する。
- 到着の間隔で、出所の種類は絞れる。50 ms に 6 件 = 約 8 ms 間隔 = このリポジトリの
  フィクスチャが使う 10 ms ticker。被験体のゴルーチン構成で出せない数なら、外から
  来ている。
- 直すときは報告された個体でなく型に当てる(§11)。#932 / #933 の修正を 2 つの
  フィクスチャにしか入れず、同じ型が 4 件再発した。

### 8. 固定パスのデバッグダンプを読むハーネスは、前のケースの答えを読む

いつ読むか: GUI や daemon を何通りかの入力で起動し、出力を読むハーネスを書くとき。

プロセスが固定パスに書くデバッグダンプ(waired-tray の
`$TMPDIR/waired-tray-debug.json`)を、ケースを順に回すハーネスで読むときは、ケース
ごとに `TMPDIR` を分ける。共有すると、前のケースのプロセスが終わりきる前に上書き
するか、新しいプロセスが書く前に読んでしまい、答えが 1 つずれる。

waired-agent#1205 のトレイの描画確認で、5 ケース(404 / 空 / 軽い / 上位 / 2 件)を
1 つのダンプパスと 1 つのポートで回したところ、`none` が軽いモデルの行を、
`lighter` が上位モデルの行を返した。`pkill` + `sleep 1` + `rm -f` を挟んでもずれた
ままで、「トレイが違う行を描いている」という製品の欠陥として報告しかけた。ケース
ごとに `TMPDIR` と待ち受けポートを分けたら正しくなった。

- 出力パスをケースごとに分ける。待ち受けポートも分ける。
- 各ケースの子プロセスは `kill` + `wait` で回収する。
- ずれた結果を見たら、製品より先にハーネスの共有資源を疑う。§7 は入力側、これは
  出力側の共有。

### 9. 計測ハーネスのログ行は、書き込みと同じ分岐の中で出す

いつ読むか: 計測用のスタブやハーネスを書くとき。その出力を issue・PR・knowledge
note に転記する前。

waired-agent#1314(2026-09-12)の計測スタブで起きた。非ストリーム応答を保持する
ループが、こういう形になっていた:

```python
if mode == "n-silent":
    continue
if mode == "n-1xx":
    self._informational(100, "Continue")
elif committed:
    self._chunk(b" ")
frames += 1
log(ev="early_byte", frames=frames, held_s=...)   # ← 分岐の外
```

`n-pad` でまだコミットしていない間は、どの枝にも入らないので 1 バイトも書いて
いない。それでも `early_byte` が 5 秒ごとに記録される。ログだけ見ると「240 秒より
前からクライアントに送っている」と読め、その読みで記録を書きかけた(実際は仕様
どおり沈黙していて、結論は変わらなかった)。

計測ハーネスの出力は、後から実測値として転記される。コードを読み直さない限り
検証されないので、ログが実際の I/O とずれていると、そのまま「測った」として
公表される。

- ログ行は書き込みと同じ枝の中に置く。書かなかった周期には別のイベント名を出す
  (`silent_tick` など)。「何もしなかった」も観測結果である。
- ハーネスのカウンタ(`frames` など)は、送信が成功した直後にだけ増やす。
- 結果を転記する前に、イベント名とコードの枝を突き合わせる。数字の妥当性(単調か、
  間隔が合っているか)だけでは、この種のずれは見つからない。

ハーネスが空のまま成功できないようにする決定は
`docs/decisions/20260829/1500-a-harness-reports-what-it-observed.md` に在る。

### 10. 複製が N 個あると、それぞれ別のものを忘れる

いつ読むか: 同じ主張・手順・ハーネスが複数の場所に在るものの 1 か所を直すとき。
3 OS 版のハーネスの 1 つだけを読んだとき。

同じ主張や手順が N か所に複製されていると、N 個が同じように古びるのではなく、
それぞれ違うものを忘れる。1 か所を読んで正しく見えても、残りが正しい根拠に
ならない。複製を見つけたら全部を並べて差分を取る。

実例(2026-08-29 前後):

- import コマンドを印字する場所が 3 つあり、`--engine-version` を書いているのは
  `scripts/dev/agentgrade-sweep.sh` だけ、`--retrieved` は workflow の shapes 行だけ
  だった。workflow の agentgrade 行は、そのまま実行すると失敗していた(誰もコピー
  して走らせていなかった)。
- `.gitignore` の `cmd/` の列挙が 4 つ中 3 つで、15 MB の ELF が 21 個のチェックを
  通ったまま公開リポジトリに入った。
- 失敗時のログ収集のインラインのブロックが 3 つあり、それぞれ別の OS・別の
  ファイルを忘れていた(`scripts/ci/collect-engine-diag.sh` 1 本に畳んだ)。

**3 OS 版のハーネスは、他の OS 版のコメントを grep して突き合わせる。** macOS の
失敗時の収集が engine.log を 1 度も採れていなかった(waired-agent#1156)。直しは
新しい仕組みではなく、他の OS 版が既に書いていた但し書きの引き写しだった。Linux の
`installtest-run.sh` は、ホストを purge するブロックに「Lean configuration only —
the engine-bearing legs would lose what they built」と書いて 4 構成を除外しており、
teardown の uninstall も Linux と Windows は「the runner is disposable」と書いて
飛ばしていた。macOS だけ、どちらの条件も無かった。

- 3 OS 版があるものは、1 つの版のコメントを grep して、他の版に同じ条件が在るかを
  見る。規則が散文で書かれている側が正しく、書かれていない側が漏れていることが多い
  (CLAUDE.md §Cross-OS parity の裏返し)。
- 除外を足す前に、そのテストが別のジョブで回り続けることを確かめる(この件は、
  lean 構成(エンジンを持たない側)の macOS のジョブで `--clean` が PR ごとに回って
  いた)。
  確かめずに足すと、テストを黙って止める。
- 直すときは 1 か所だけ直さない。`git grep -F '<逐語の一文>'` で複製を数え、数が 1 で
  なければ、導出に寄せられないかを先に考える(期待値を `cmd/*/` から導出する、
  reflect で全フィールドを歩く、1 本のスクリプトを 3 OS で走らせる。`shell: bash` は
  windows-latest では Git Bash なので 1 本にできる)。

### 11. フレークを洗い直すときは、報告された個体でなく型に当てる

いつ読むか: フレークを直すとき。「既知のフレークは 0」と言う前。

2026-08-20 の洗い直しで「unit tests のジョブの既知フレークは 0」にしたが、
2026-08-28 に `main` の直近 60 ラン(ci.yml)を調べると失敗が 4 件、うち 3 件が
未起票の別のフレークだった。前回の修正が、報告されたフィクスチャ 2 つにしか入って
おらず、同じ型が再発していた。

- 起点は `main` の直近のランの失敗。
  `gh run list --workflow=ci.yml --limit 150 --json … | select(.conclusion=="failure")`
  → `gh run view <id> --log-failed | grep -E "^--- FAIL|_test.go:[0-9]+:"`。
  モジュールプロキシの障害(`proxy.golang.org` の stream error)は分類して除外する。
- ヘルパを作ったら、同じ形の全フィクスチャに通す。
- 再現できないものを「直した」と言わない。waired-agent#925(TempDir not empty、報告は
  windows / darwin)は、linux で 20 スイート × `-count=2` × 2 倍の過負荷でも出なかった。
  名前を付けられた寿命の穴(warm のゴルーチンの未 join、エンジンの未停止)だけを塞ぎ、
  `Refs` で出した。issue は open のまま(2026-09-21 時点)。
- issue に書かれた原因の仮説は、確かめてから使う(#1008 の「2 つのループが合成する」は
  偽だった)。フレークの裏に製品の穴が居ることがある
  (`docs/knowledges/20260921/2110-timing-and-concurrency-test-shapes.md` §5)。
- `unit tests (darwin)` / `(darwin, seeded host)` / `(windows)` は required ではない
  (2026-09-21 時点)。マージは止めないが、`main` の失敗として残る。
- 直す前に、revert して落ちることを確かめる(PR #368 の基準)。フィルタやゲートは
  両方向を固定する(全部通す・全部落とすのどちらも症状が出ない)。
- 待ちは `waitUntil` / `waitBackstop`(`cmd/waired-agent/wait_backstop_test.go`)を使い、
  GOOS の分岐や CI の環境変数で逃げない。余裕が要るのは上界のアサートだけ
  (waired-agent#384 の規則。寸法の決め方は 2110 の §1)。

### 12. シェルのハーネスとガードで、grep が黙って通る 5 つの形

いつ読むか: `scripts/ci` のガードやシェルのハーネスで grep を使うとき。

どれも失敗が「通る」側に倒れるので、自己テスト(関数だけ `sed` で取り出して `eval`
し、ケースを流す)か、直しを戻して落ちることの実測でしか見つからない。

1. `grep -F` に複数行を渡すと、複数のパターンになる。末尾に改行があると 1 つが
   空文字列になり、何にでも一致する。比較対象は自分で正規化して 1 行の marker に
   する(`<!-- red-lanes: a;b -->`)。経緯は
   `docs/knowledges/20260829/1530-rotating-logs-and-one-line-surfaces.md` §3。
2. `-` で始まるパターンは grep のオプションとして解釈される。
   `scripts/dev/installtest-dash.sh` の `run_case_asserts` は `grep -Eq "$want"` を
   `--` 無しで呼ぶ。`!-- --log-level` のようなパターンは
   `grep: unrecognized option` を stderr に出して、アサートは通る(FAIL_RE にも
   掛からない)。`waired-agent install.*--log-level` のように、`-` 以外で始まる形に
   書く。`scripts/dev/installtest-pwsh.ps1` は `$out -match $want` なので、この形は
   dash のハーネスだけ。
3. `set -e` + `pipefail` 下の `x="$(… | grep …)"` は、一致ゼロでスクリプトごと落ちる。
   `if … | grep -q …; then` の形は `if` が `set -e` を抑止している。代入に書き換える
   なら `|| true` が要る(同じく 1530 の note §3)。
4. `grep -c` は 0 件のとき `0` を印字して exit 1 する。`n=$(grep -c . f || echo 0)` は
   `"0\n0"` になり、`[ "$n" -eq 0 ]` が `integer expression expected` で落ちる。
   `[ -s f ] && n="$(grep -c . f || true)"` と書く。
5. `grep -c` は対象が 1 ファイルだとファイル名を前置きしない。
   `grep -rc pat dir/*.go | awk -F: '{n+=$2}'` は本番(多数のファイル)では動くが、
   ガードの自己テストが作る小さな木では常に 0 を数える。
   `grep -rho pat … | grep -c .` にする。

否定アサート(「この文字列が出ないこと」)は通るのが正常なので、壊れていても見分けが
付かない。足したら、直した欠陥を一時的に戻して落ちることを実測する。観測する出力が
どこにも出ていないなら、先に観測できるようにする(例: スタブの `waired-agent` に
`printf 'STUB waired-agent argv: %s\n' "$*" >&2` を足して、登録時の argv を出した)。

### 13. ガードと生成物の照合が何も検査しなくなる 4 つの形

いつ読むか: `scripts/ci` のガードを書く・対象を広げるとき。生成物を定義ファイルと
照合するテストを書くとき。

ガードは「何を監視するか(対象)」と「何をもって合格とするか(条件)」に分けて読む。
何も検査していないガードは通って見えるので、自己テストと変異(§1)でしか見つから
ない。今日の木で通るだけの自己テストは、ルールが無くても通る。

**13a. 合格条件が、その変更で回す生成ステップの出力で満たされる。**
`scripts/ci/docs-surface-guard.sh` は「対象パスを触ったら `docs-site/` 配下も触れ」。
カタログを対象に足そうとしたが、マニフェストの変更後に回す `make catalog-docs` が
`docs-site/src/data/model-sizes.json` を生成するので、合格判定 `^docs-site/` を
生成ステップ自身が満たしていた(waired-agent#1119)。lockfile も同じ形。

- 対象を広げる前に、条件が生成物で満たされないかを見る。合格条件のパスから生成物を
  明示的に除外し、除外リストの綴りと生成側の定数が一致することをテストで結ぶ。
- 自己テストに「対象＋生成物だけ」のケースを入れる。
- 決定の本体は `docs/decisions/20260829/1500-a-harness-reports-what-it-observed.md`
  §2・§4。

**13b. 生成物を定義ファイルと照合するときは、値の存在でなくキーとの隣接で見る。**
`versioninfo.json` とコミット済みの `.syso` の照合を `have[key] && have[value]` で
書いたら、`FileDescription` を `waired` に書き換えても通った。`waired` は
`InternalName` の値として既にリソースの中に在った(waired-agent#1209)。生成物は
定義の語彙でできているので、集合で見るとどの値もだいたい在る。順序付きの列として
読み、`key` の次が `value` であることを見る。

- 試す変異は「値だけを、別の正しい値に書き換える」もの。パスやキーを消す変異は
  どんな実装でも捕まるので、根拠にならない。
- 経緯は `docs/knowledges/20260905/2000-windows-version-resources-two-writers.md` §8。

**13c. 読み手が別のパッケージに居る生成物は、実際の読み手に読ませるテストを 1 本
置く。** テンプレートから書くファイル(OpenCode / OpenClaw のプラグイン)を
`internal/integration/detect` の正規表現と `topup.go` が読んでいるのに、既存テストは
全部が手書きのフィクスチャだった。コンパイラの関係が無いので、テンプレートを編集
しても読み手側は通ったまま壊れる。「生成して、書いて、実際の読み手に読ませる」
テスト(`internal/integration/openclaw/detect_adjacency_test.go`)は、初回で 2 件
捕まえた。

- 生成ファイルのコメントも照合の対象になる。テンプレートのコメントに書いた例示
  (`baseURL: "<url>"`)が、検出器の `FindSubmatch`(最初の一致)に先に当たった。
  例示を書くなら、照合される綴りを避ける。
- 行末を `$` で固定した読み手は、Windows の CI でだけ外れる
  (`docs/knowledges/20260912/1230-embedded-templates-are-crlf-on-windows.md`)。

**13d. 除外マーカーは直上 1 行でなく、連続するコメントブロック全体で探す。** 除外を
現場に書かせるガード(CLAUDE.md §Test discipline「A guard's exemption is keyed at
the site」、waired-agent#1103)で `// background: <why>` を要求したが、書く価値の
ある理由は 1 行に収まらず、マーカーは複数行コメントの先頭行に来る。直上 1 行だけを
見る実装は、実在の除外 12 か所を全部拒否した。`//` で始まる行を上へ遡り、どこかに
マーカーがあれば通す(`scripts/ci/provider-fixture-ctx-guard.sh` がこの形)。
