# タイミングと並行に依存するテストの型 (20260921 21:10)

## Issue

時間の余裕、ゴルーチンの順序、`-race` に依存するテストが、フレークするか、何も
検査しないまま通る型をまとめる。寸法の決め方には実測値が在るので、次に同じ種類の
テストを書くときの出発点にする。タイミングに依らない型は
`docs/knowledges/20260921/2100-tests-that-pass-without-testing.md`。

セッションのメモリに在った知見を、オーナーの指示(2026-09-21、
waired-ai/waired-ai#12)でリポジトリへ移した。

## Learnings

### 1. 上界テストの余裕は、比でなく絶対差で取る

いつ読むか: 「この間隔は境界を超えない」型のテストの寸法(sleep の長さ、境界、本数)を
決めるとき。「1 回落ちて、再実行で通る」テストを直すとき。

実測(14 コアのホストでスピンするゴルーチンを 56 本 = 4 倍の過負荷、1 設定あたり
3000〜6000 個の間隔(gap)):

| sleep の長さ | p50 | p99 | max | 遅れ(max − sleep) |
|---|---|---|---|---|
| 10 ms | — | 55.2 ms | 203.6 ms | 193.6 ms |
| 50 ms | 60.7 ms | 86.9 ms | 219.5 ms | 169.5 ms |
| 50 ms(別のサンプル) | 60.6 ms | 84.2 ms | 583.2 ms | 533.2 ms |

スケジューラに実行を回してもらえないことによる遅れは、sleep の長さにほぼ無関係な
加算量だった。`bound / gap` の比を上げても効かず、効くのは `bound - gap`。さらに、
gap の本数は分布の裾からの抽選の回数なので、同じ余裕なら「少数の大きい gap」のほうが
安全(本数 ≈ bound / gap のトレードオフ)。

- 失敗率を測ってから寸法を決める。`bound を超えた gap の割合 × 本数` が 1 実行
  あたりの失敗率になる(waired-agent#931 の旧設定は 0.63 % × 10 = 6.2 % / 実行で、
  これが「1 回落ちて、再実行で通る」の正体だった)。計測は使い捨てで書ける。負荷は
  プロセス内のゴルーチンで作る(シェルの `while :; do :; done &` は、シェルが
  終わっても残る)。
- 合計時間で余裕を測らない。成り立つべき性質は gap ごと。
- 最後の書き込みの後に sleep を置かない。遅れに晒される区間が 1 つ増えるだけ。

### 2. 時間の下界と回数の下界は、遅れに対する向きが逆

いつ読むか: タイミングのテストに余裕を足す前。上界か下界かを先に判別する
(waired-agent#384 が規則を明記している)。

- 時間の下界(「境界を過ぎるまで待つ」)は、遅れ(overshoot)で真になるだけなので
  触らない。同じパッケージ変数を逆向きに引く兄弟のテストが居ることが多い
  (`internal/download` の `FetchStallTimeout`)。
- 回数の下界は逆向き。「N 回以上ポーリングした」は、遅れで偽になる(回数 = 予算 ÷
  間隔。50 ms ÷ 5 ms = 10 回のはずが、Windows の runner で 3 回だった。
  waired-agent#1221)。直しは予算だけを広げる。フェイクが有限回で答えるなら、
  実行時間は増えない。
- 回数の上界は安全。
- 2 点の時刻の順序を `time.Now()` の比較で決めるテストは、Windows と macOS の CI で
  だけ落ちる。`docs/knowledges/20260912/1400-clock-resolution-is-an-os-property.md`。

### 3. ワイヤに載る期限は、形式の精度が下限になる

いつ読むか: 期限やタイムアウトを縮めてテストを速くするとき。

`time.RFC3339` は秒精度。`now + 150ms` を `Format(time.RFC3339)` に通すと現在の秒に
丸まり、受け取った側では既に期限切れになる。waired-agent#1175 の poll 予算のテストは
通っていたが、1 回もポーリングせずにループの冒頭で終わっていた(修正を revert
しても通った)。

- 縮めてよいのは自分のコード側の定数(猶予・下限・ポーリング間隔。var の seam に
  する)。ワイヤに載る期限は、秒精度なら 2 秒以上にする。

### 4. 経路を通ったことのアサートを 1 行置く

いつ読むか: §1〜§3 のテストを書いたとき、またはその本数や時間を削って高速化するとき。

上界テストには「合計の経過が bound を超えたこと」、期限切れのテストには
`pollCount > 0` のように、経路を通ったことのアサートを置く。置かないと、後で本数を
削って高速化した変更が、何も証明しないテストを通す。エラーの種類だけを見ていると、
そこへ着く前に別の理由で終わったケースを拾えない。修正を revert して落ちることも
確かめる(手順は 2100 の note の §1。revert が実際に当たったかも見る。文字列置換は
一致しなければ何も変えずに終わる)。

### 5. スケジューリングの事実で、製品の判断をゲートしない

いつ読むか: `awaitX()` が「実際に待ったか」を返しているのを見たとき。テストが
`time.Sleep` で「ゴルーチンが park した後」を作ろうとしているとき。

`awaitX()` が返す「実際に待ったか(`waited`)」は、スケジューラの事実であって製品の
事実ではない。それでその後の再確認をゲートすると、park しなかった経路が再確認を
丸ごと通らない。

実例(waired-agent#1086 → PR #1114): `holdBundledPrePull` は 20〜45 GB の
ダウンロードの直前に「setup が別のモデルを指名していないか」を再確認するが、それが
`awaitModelChoice` の `waited` でゲートされていた。claim が無いホスト(ブラウザで
設定しただけの普通のホスト)と、claim が直前に取り下げられたホストは
`waited=false` になり、再確認を丸ごと飛ばして dispatch する。手前に
`applyHostCutoff`(ホストの速度の計測 = 数分)が挟まるので、競合が起き得る区間は
広い。waired-agent#305 の二重ダウンロードそのものだった。

#1086 は「macOS の runner が遅くて 50 ms を外した」という報告だったが、決定的に
した版のテストは `origin/main` で毎回落ちた。フレークは製品の穴の現れだった。
テストが `time.Sleep` で park の後を作ろうとしていたら、「なぜ park の有無が結果を
変えるのか」を先に問う。変えてはいけないことが多い。

- 直し方: ゲートを外して再確認を無条件にし、`waited` の戻り値ごと消す。そのとき
  「二度呼ぶコスト」が、既にゲート内で二度呼んでいた形と同じかを確認する。
- テストは両方向を閉じる。落ちる方向(順序が遅れて dispatch)は製品の修正で消えるが、
  誤って通る方向(先に指名してしまい、手前の分岐で立ち下がる)が残る。
  - 前段の解放は、ログ行を `waitUntil` で観測する(製品が出す文字列を定数にする)。
  - 後段は、既存の mutex や seam でゴルーチンをその段に留める(例:
    `p.hostSpeedMeasureMu` をテストが Lock して、host-cutoff の段で止める)。
  - 「どちらの分岐で立ち下がったか」をログ行でアサートする。空のタグ配列は両方の
    分岐が作るので、それだけでは何も固定していない。
- ゲートが効かなくなったら落ちる設計にする。効かなければ dispatch が走ってタグが
  増える = 落ちる。黙って通らない。

### 6. 順序が一瞬反転する区間の中身がログ 1 行だけなら、観測点は logger

いつ読むか: 「A を先にすると一瞬 X になる」型の順序の欠陥にテストを書くとき。

waired-ai/waired#1305 で起きた。`cmd/waired-agent/share_control.go` の `Unshare` が
`setSuspended(false)` を先に呼ぶため、suspend 中は `IsSharing()` が
false → true → false と一瞬戻る。その競合が起き得る区間(race window)の中身は、
同期的なログ 1 行だけだった。

素直なテスト(stop のフックでゲートを読む)は、壊れた順序でも通る。フックはフラグを
保存した後に走るので、その区間を過ぎている。実際に旧順序へ戻して確認したところ、
PASS のままだった。

効いた形(`cmd/waired-agent/share_control_test.go`): `slog.Handler` を自前で実装し、
`Handle` の中で毎レコード `sc.IsSharing()` を読んで、開いていたらそのレコードの
`Message` を記録する。旧順序では
`the gate was open during Unshare, at "sharing suspension change"` と、その区間を
占めている当のログ行を名指しして落ちる。

- まず、その区間の中で何が起きているかを数える。ネットワークやディスクなら既存の
  seam が在るが、ログしか無いなら logger が唯一の観測点になる。
- `Enabled` は常に true を返す(Debug のレコードも要る)。
- armed フラグを置いて、対象の操作の間だけ観測する。
- 修正の前後で、戻して落ちることを見る。新しい述語だけを呼ぶテストは、その述語が
  正しいことしか言わない。

### 7. 手で立てた実行中フラグは defer で戻す

いつ読むか: フィクスチャに「detach した仕事が終わるまで待つ」join を足すとき。
足した後にスイートが遅くなったとき。

`cmd/waired-agent` のフィクスチャに、detach した仕事の終了を待つ cleanup を足した
直後、パッケージのスイートが 34 秒から 42 秒に伸びた。原因は失敗でも遅い
ゴルーチンでもなく、呼び出しの合流(coalescing)を起こすために
`p.engineReconcileInFlight` / `warmInFlight` / `engineStartInFlight` を手で
`Store(true)` して、そのまま返すテストが 4 本あったこと。join から見ると「永久に
仕事が実行中」なので、上限(2 秒)まで回して、諦めた旨のログを出す。

手で立てたフラグは状態であって、テストの終わりに勝手には戻らない。join を持つ
フィクスチャでは、その状態が次の判定の入力になる。

- `Store(true)` の直後に `defer …Store(false)` を置き、なぜ戻すのかを 1 行書く。
- join を足す変更では、スイートの所要時間を前後で比べる。伸びていたら、どこかで
  フラグが戻っていない。
- `-v` で回して join が諦めたログを grep すると、どのテストかがすぐ分かる。

### 8. `-run` で絞った `-race` は、全体の `-race` の代わりにならない

いつ読むか: 呼び出しを超えて生きるゴルーチンを新しく作る変更を入れたとき。

`go test -run 'X|Y' -race -count=3` が通っても、`go test ./... -race` は落ち得る。
競合の相手が「別のテストが残したゴルーチン」である場合、`-run` で絞るとその相手が
起動しないので、永久に検出できない。ゴルーチンの寿命を延ばす変更では、パッケージ内の
無関係なテストが被害側にも加害側にもなる。

実例(waired-agent#821 / PR #921): 待ちが `runPullJob` の呼び出しを超えて生きるように
した結果、`PullModel` を叩く別のテストが待ちのゴルーチンを残し、こちらのテストの
`Cleanup` によるパッケージ変数の書き戻しがその下で走った。手元は絞り込んだ `-race` で
通り、CI の `unit tests (linux)` が本物の `WARNING: DATA RACE` で落ちた。

- ゴルーチンの寿命を延ばす変更を入れたら、マージ前に一度 `go test ./... -race` を
  回す。絞り込みは反復用で、証拠にはならない。
- テスト用の調整値は、パッケージ変数でなくプロバイダや構造体のフィールドに置く
  (`cmd/waired-agent/host_cutoff.go` の `hostSpeedWindow` が「a field, not a package
  var, so the tests that shrink it stay parallel-safe」と書いている)。
- 待ちのループは、毎周「まだこの作業をしたいか」を問い直す形にすると、所有者が
  片付いた時点でゴルーチンも終わる。競合の相手そのものが消える。

同型の既存の欠陥は waired-agent#925(フィクスチャが `reconcileEngineServe` を join
していない。2026-09-21 時点で open)。`httptest` のリスナを介して別のテストの
ゴルーチンが入り込む型は 2100 の note の §7。
