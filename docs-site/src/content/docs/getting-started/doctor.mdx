If something is wrong and you try only one thing, try this:

```sh
waired doctor
```

It checks every part of the setup in turn and prints one line per check.
Then, if anything it can repair is broken, it offers to repair it.

## Reading the output

Each line is a symbol, the thing checked, and what was found.

    that host are left out: this block shows the all-ticks case, and the table
    below explains ⚠. Re-capture, don't edit, when the product wording moves. */}
<Expected>
```

✓ waired phase — active — overlay routing in effect

✓ claude-code statusline — installed, and this computer's shell can run it
```
All ticks. Nothing to do.
</Expected>

| Symbol | Plain | Meaning |
|---|---|---|
| **✓** | `*` | Fine. |
| **⚠** | `!` | Working, but not the way it should be. Worth reading, not urgent. |
| **✗** | `x` | Broken. Something you are trying to do will not work. |
| **·** | `-` | Not checked. The line says why, usually that it needs administrator rights. |

The **Plain** column is what you get where the symbols cannot be written: a
Windows console that is not on UTF-8, output redirected to a file on Windows,
or a terminal whose locale is not UTF-8. Everything else about the line is the
same.

When anything is not a ✓, the command finishes with a non-zero exit code and a
count. That is useful in a script and ignorable when you are reading it
yourself.

## Pressing f

If any finding can be repaired automatically, you are asked:

<Expected title="At the end of the output">
```
Press f to fix [f/N]:
```
</Expected>

Press `f`. What it repairs depends on what the check found:

- A coding tool that is not set up to use Waired: it reapplies the
  coding-tool setup, the same work as `waired link all`.
- On a Linux desktop, a missing or switched-off AppIndicator extension: it
  installs and enables it.
- An inference engine that is not running, when the background service has
  said why: it asks the service to start the engine, the same request
  `waired inference engine start` makes.

Then it tells you to run the check again. A coding-tool repair prints:

```
Running repair (waired link all)...
Done. Re-run `waired doctor` to verify.
```

An engine repair prints the service's reason, then hands over the start:

```
Starting the inference engine...
  It is not running because: no vLLM-capable model selected — set a preferred model that ships a vllm/safetensors variant (e.g. gpt-oss-20b)
  Asked. `waired inference engine status` reports when it is running.
Done. Re-run `waired doctor` to verify.
```

"Asked", not "started": a large model takes minutes to load, so the service
accepts the request and the engine comes up in the background. If the service
declines, for instance because local inference is off on this computer, the
repair prints a warning that begins `warn: the inference engine was not
started:` and ends with the service's own reason.

<Aside type="note" title="What f does and does not touch">
	The repair touches your own coding-tool configuration in your home
	directory, the desktop's AppIndicator extension, and the engine the
	background service runs. Nothing else. It does not reinstall Waired, does
	not sign you out, does not touch models, and never edits a config file
	inside one of your projects.
</Aside>

To repair without being asked, in a script or over SSH:

```sh
waired doctor --fix
```

## What each check means

| Check | What a failure means | Usual fix |
|---|---|---|
| **state directory** | Waired's own folder for identity, secrets, and records holds no identity while the background service is signed in, so the folder was emptied while Waired was running. A folder this account cannot read is a different line, and a skipped check rather than a failure. | [Sign in again](/getting-started/sign-in/#sign-in-again) to put the identity back. |
| **device sign-in** | This computer's sign-in is no longer valid. Your model keeps working locally, but the computer no longer appears in your account, and your other computers cannot reach it. | `waired init`. See [I signed in, but Waired says I am signed out](/troubleshooting/install-and-sign-in/#i-signed-in-but-waired-says-i-am-signed-out). |
| **network connection** | You are signed in, but this computer has not connected yet. Waired keeps retrying on its own. | Wait a minute and run the check again. |
| **device key** | Your network is using a different key for this computer than the computer itself holds. Your own model keeps working, but no other computer can reach this one. Silent when the two agree. | `waired init` to register the computer again. |
| **waired-agent service** | The background service is not running, and this line says why, read from the operating system's own service records. | Start it from the Waired menu, or follow the suggestion in the line. |
| **waired-agent management** | The background service is not answering. This is the one that stops everything else working. | See [A command says “waired-agent is not running”](/troubleshooting/no-answer/#a-command-says-waired-agent-is-not-running). |
| **waired phase** | Routing is paused, or in an unexpected state. | `waired resume`. See [Pause or stop Waired](/guides/pause/). |
| **Local Gateway** | The service is up, but the part that answers requests is not. A `503` usually means no model is loaded yet. | Wait for the download to finish (`waired models ls`), or [check your model](/guides/choose-a-model/). |
| **coding-agent entries** | Claude Code, OpenCode, or OpenClaw is not configured to use Waired. | Press `f`. |
| **claude-code statusline** | Installed, but written for another operating system's shell, on a Windows computer set up by an older Waired. The status line stays blank. Your model keeps answering. Silent when it is fine, and absent if you do not use Claude Code. | `sudo waired claude enable` (Windows: from an administrator terminal). |
| **&lt;tool&gt; installation** | Only a **·** here: the tool's command is not on your `PATH`, so there is nothing to configure. A leftover folder is not an installation. | Install the tool, or ignore the line if you do not use it. |
| **inference engine** | Printed on every run. A **⚠** ``paused — `waired resume` to restore overlay routing`` means routing is paused and the engine itself is fine. A **⚠** `not ready`, followed by the service's own reason, means the engine is not running. A **✓** reading ``off on this computer — requests go to your other computers or the cloud. `waired inference on` to run models here`` is a setting, not a fault. | `waired resume` for a pause. `waired inference on` to run models here. When the engine is not running and the service has said why, press `f`. That offer does not appear when you stopped the engine yourself, nor while the service is still starting. |

### Rows that are notices, not checks

Waired also prints anything it has to tell you about this computer, as a
**⚠** among the rows above. These are not checks of your setup. They are
messages that stand for as long as they are true, and they never make
`waired doctor` report a failure.

<Expected>
```
⚠ model suggestion — Lighter model recommended — switch to qwen3-8b-instruct. This computer answers at 42 tok/s with qwen3-30b-a3b, below the 60 tok/s floor.
⚠ engine version — ollama is not running the version Waired pins. engine version 0.24.0 does not match the bundled pin 0.33.3 — run `sudo waired runtimes install ollama`
```
</Expected>

The same messages appear in the Waired app and in `waired status`. For every
one of them, see [Notices](/guides/notices/).

### When your network and this computer disagree on its key

Every computer in your network has its own key, and the others use it to
reach it. If the network holds a different key than the computer does, for
example after re-registering the computer, the two can no longer talk:

<Expected>
```
✗ device key — the network is using a different key for this device than the device holds — no other computer can reach it over Waired. Run `waired init` to register this device again.
```
</Expected>

Nothing else looks wrong when this happens. The computer is signed in, shows
as online in your account, and its own model answers. Only requests between
computers fail. While a key change is still finishing you may see it as a
**·** instead. That one settles on its own.

## When the check itself cannot see everything

On a normal desktop install, some of Waired's files belong to the system.
Without administrator rights the doctor reports what it can, and marks the
checks it could not run with a **·**:

<Expected title="Without administrator rights">
```
· device sign-in — needs elevation to check; run `sudo waired doctor`
· waired phase — needs elevation to check; run `sudo waired doctor`
```
</Expected>

On a computer where Waired was installed for everyone, the identity itself
belongs to the system, and the doctor names where it lives:

<Expected title="A system-wide install, without administrator rights">
```
· state directory — this device is enrolled system-wide; its state (/var/lib/waired) needs elevation to check; run `sudo waired doctor`
```
</Expected>

A **·** never counts towards the exit code. To close the gap, run the check
with administrator rights.

<Tabs syncKey="shell">
	<TabItem label="macOS / Linux">
		```sh
		sudo waired doctor
		```
	</TabItem>
	<TabItem label="Windows">
		From **Terminal (Administrator)**:

		```powershell
		waired doctor
		```
	</TabItem>
</Tabs>

Running it with `sudo` does not switch the check over to the administrator's
own setup. Your coding tools are configured in your home folder, so that is
what gets checked, and the first line says whose:

<Expected title="At the top of the output">
```
Running under sudo — checking the setup for user "you", not root.
```
</Expected>

Pressing `f` after an elevated run repairs that same setup, as you.

<Aside type="tip" title="Sharing the output">
	`waired doctor` prints file paths, so read the output before you paste it
	into a bug report. `waired logs --mask-pii` masks your home folder,
	username, machine name, and account email in the log file it collects.
</Aside>
