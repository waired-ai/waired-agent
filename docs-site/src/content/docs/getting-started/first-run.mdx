**Installing normally does this for you.** The install command starts Waired
and then goes straight into sign-in, so a first-time setup is covered by the
[Quickstart](/quickstart/) and you never type `waired init` yourself.

This page is for the times you do:

- setup was interrupted and you are resuming it
- you installed with `--no-init`
- you are setting up a server with no desktop
- you want to know what each choice actually does

<Aside type="tip" title="Same account = same network">
	Sign in to **every** computer with the **same Google account**. That shared
	sign-in is what lets one machine use another's AI. Different accounts make
	separate, unconnected networks.
</Aside>

## Start it

<Tabs syncKey="os">
	<TabItem label="Windows">
		Open **Terminal (Administrator)** — right-click the Start button — and
		run:

		```powershell
		waired init
		```

		<Aside type="note" title="“waired is not recognized”">
			The installer added Waired to your system path, but a terminal
			opened *before* the install still has the old one. Open a **new**
			Administrator terminal. If you would rather not, run it by full
			path: `& "C:\Program Files\Waired\waired.exe" init` — adjusting the
			folder if you chose a different install location.
		</Aside>
	</TabItem>
	<TabItem label="macOS">
		```sh
		sudo waired init
		```
	</TabItem>
	<TabItem label="Linux">
		```sh
		sudo waired init
		```
	</TabItem>
</Tabs>

It prints a sign-in link and waits:

<Expected>
```
Sign in using this link:
  https://app.waired.ai/login/…

Control Plane: https://app.waired.ai

>> Press Enter to open your browser (or open the link above yourself)...
```
</Expected>

Press **Enter** and choose your Google account. You can also copy the link into
any browser, on this computer or another one — the terminal does not wait on
that keystroke, and picks up as soon as you are signed in.

<Aside type="caution" title="Leave that window open until setup finishes">
	Installing the AI software needs administrator rights, and a web page cannot
	grant them. **This command is what actually performs those steps** while the
	browser page drives them.

	If you close it, the browser says *“The setup command on … was closed before
	this finished. Your progress was saved.”* Run the same command again to carry
	on — nothing is lost, and any model download continues regardless.

	Re-running it does not sign you in again: it says *“Already signed in as
	you@example.com — resuming setup”* and picks up where it left off. Signing in
	again is `waired init --force-reauth`, and Waired does it by itself only when
	the existing sign-in has expired beyond repair.
</Aside>

## Finish in the browser

After sign-in your browser lands on the setup page for this computer. Pick a
model, press **Continue**, and it reports what the computer is doing,
live:

<Screenshot
	src="setup-wizard-progress.png"
	alt="The Waired setup page in a browser, showing three steps — Install the AI software (done), Download the AI model (in progress, with a bar reading 7.9 GB of 19.2 GB), and Check the speed (waiting)."
	caption="Every step is reported by the computer itself. Closing this tab does not stop them."
/>

| Step | What is happening | How long |
|---|---|---|
| **Download the AI software** | Fetching the program that loads and runs models — around 1.5 GB for the standard option, around 4 GB for the high-performance one. The page shows how far it has got and how fast it is going, the same figures the terminal shows. | A few minutes |
| **Install the AI software** | Unpacking and setting it up. This is the part that needs administrator rights — which is why the terminal window has to stay open. | A minute or two; up to 15 for the high-performance option |
| **Connect your coding tools** | Pointing the coding tools you ticked at Waired. Also administrator work, so it is the terminal that does it — and it is done before the long download rather than after, so nothing is waiting on you later. | Seconds |
| **Download the AI model** | The AI itself, several gigabytes. | 5–30 minutes |
| **Check the speed** | A short measurement, so Waired knows whether this machine keeps up. | Up to 5 minutes |

The download step only appears when there is something to download: a computer
that already has the AI software goes straight to the next step. The
coding-tools step only appears when the page asked you about them.

<Expected>
	Every step ticked, and **“Everything's ready — this computer can now run AI
	on its own.”** Press **Go to device**.
</Expected>

While the browser is driving, the terminal asks you nothing. It reminds you to
leave it open, and — when the setup page has asked which coding tools to
connect — it is this window that writes them, because that needs administrator
access the page does not have:

```
Keep this terminal window open until setup finishes — it does the parts the
browser can't.
🔌 Setting up your coding tools (claude-code, openclaw)…
```

Ticking **Claude Code** there does what the page says it does: it points
Claude Code at Waired for everyone who uses this computer. The other tool
only drops a file in your own home folder. This is the same routing the
terminal asks about after a non-browser install, decided in the browser
instead — and `--skip-claude-proxy` at install time still overrides it.

On an older setup page, which does not ask, it tells you how to do it yourself
instead: *“You can set up your coding tools later from this terminal with
`waired link all`.”*

That happens **before** the model download, which is deliberate: it is the last
thing on this computer that needs administrator rights, and putting it behind a
download that can take an hour meant coming back to a setup that had been
waiting for you. So the terminal is finished with its share by the time the
download starts, and says so — *“Setup is continuing in your browser — nothing
more is needed from this terminal”*. You can close it from then on. The model
download and the speed check do not need it, and the coding tools stay
connected whether the window is open or not.

If you leave it open, it keeps showing the download's progress. That is the
only reason to.

<Aside type="note" title="The setup page is in English">
	The web console is English-only for now. Translations are planned.
</Aside>

## Set up in the terminal instead

At *“Setup is continuing in your browser…”*, press **Enter**. Nothing moves
yet — the terminal first says what taking over means and asks you to confirm:

<Expected title="You are asked">
```
   Taking over means this terminal drives setup and the browser page stops.
   Any model download keeps running either way.
   Take over setup in this terminal? [y/N] (default: No)
```

Answer **y** to take over. Pressing Enter again answers *No*, so a keystroke
you did not mean cannot move setup out of the browser; the offer stays open
if you change your mind.
</Expected>

The offer closes once you press **Continue** in the browser. From that
point this window is running the installation, and the terminal says so:

<Expected>
```
Setup has started in your browser — this window now runs the installation.
```

Enter still answers, but it no longer switches:

```
Setup is running in your browser and this window is doing the installation.
To abandon it, press Ctrl-C and run the setup command again.
```

Abandoning costs the work in progress, which is why it takes a deliberate
Ctrl-C rather than a keystroke. If the browser tab is what went wrong, you do
not need this: open the computer's page again and choose **Resume setup**.
</Expected>

What the terminal asks after that depends on how it is running.

### After a normal install

The terminal asks about your coding tools, and nothing else — the model was
chosen in the browser, or by the installer. Both questions come **after** the
model has finished downloading, so nothing interrupts the transfer:

<Expected title="You are asked">
	Whether to set up coding-agent integration, then whether to route Claude
	Code through Waired. Answer **Y** to both.

	Answering no to the routing question leaves the connection installed but
	inactive; turn it on later with `sudo waired claude enable`.
</Expected>

### <a id="no-desktop-no-browser"></a>On a server, or with no browser

With `--no-browser`, `--non-interactive`, or on a machine where Waired cannot
reach a running service to hand over to, `waired init` does the whole job
itself and asks the full set of questions:

<Steps>

1. **Google sign-in.** Only the link and a pairing code are printed — open them
	on another device. The terminal says *“Nothing to press here”*: no key is
	needed at this step, and it notices the sign-in on its own.

2. **Run AI models on this computer? `[Y/n]`** — **Y** on a desktop or GPU box.
	**N** on a machine that should only *use* another computer's AI; it still
	joins your network as a gateway/relay. The default follows this machine's
	memory: with a model to recommend, Waired defaults to yes; a machine below
	the recommended spec is warned first and defaults to no. Which model is
	not decided here — that is step 6, after the AI software is installed and
	this computer has been measured. Change your mind later with
	`waired inference on`.

3. **Let your other devices use this computer's AI? `[Y/n]`** — **Y** on a
	machine meant to serve your laptop. This is independent of the previous
	answer.

4. **Route Claude Code through Waired? `[Y/n]`**

5. **Keep local inference on anyway? `[y/N]`** — asked only if the quick
	one-time speed measurement, taken right after the AI software is installed,
	finds this computer slow for everyday coding work. **No** (the default)
	turns local AI off; the machine still joins as a gateway/relay, and
	`waired inference on` brings it back.

6. **Choose the AI model for this computer** — a numbered list of the bundled
	models, with the one recommended for this hardware preselected; press Enter
	to take it. A model that fits but cannot keep a whole coding session on the
	graphics card says how much of its context cache is read from system RAM
	instead — the same figure `waired models ls --detail` prints. A model that
	does not fit this computer's memory at all is listed with the reason, and
	picking it anyway is confirmed explicitly (**Download it
	anyway? `[y/N]`** — **No** returns to the list). Choosing **0) Don't
	download a model now** finishes setup with the AI software installed and no
	model, which is a normal state, not an error: pick one later from the
	browser dashboard or with `waired models pull <model>`. If nobody answers
	— the terminal closed, nobody at the keyboard — nothing is downloaded:
	the question is recorded as open and Waired waits until someone chooses.
	Asked only on the first install — a machine that already has a model
	keeps it.

7. **Check the speed** — a short measurement, taken once the model is ready. If
	this computer cannot keep up, Waired offers a lighter model, names both and
	says which direction it is offering, so you can weigh the trade-off. If
	nobody answers — the terminal closed, nobody at the keyboard — the model this
	machine is running is left alone and nothing is deleted.

</Steps>

### <a id="servers-and-containers-auth-keys"></a>Servers and containers: auth keys

Sign-in normally needs a person and a browser. On a fleet of servers, or in a
container image that has to come up on its own, there is neither. An **auth
key** stands in: you create it once in the web console while signed in, and
each machine presents it instead of signing in.

Create one under **Settings → Auth keys**, then on the machine:

```sh
sudo waired init --auth-key waired_ak_...
```

Choose **one device** for a key you use once, or **many devices** for a key a
fleet or a container image shares. Keys expire after at most 90 days, and you
can revoke one at any time — revoking stops *new* machines from joining and
leaves the ones already added signed in.

<Aside type="caution" title="A key on the command line is visible to others">
	Anything in a command line shows up in `ps` for every user on the machine,
	and in your shell history. On a machine you share, put the key in a file and
	point at it instead:

	```sh
	sudo waired init --auth-key file:/etc/waired/authkey
	```

	In a container, set `WAIRED_AUTH_KEY` in the environment and drop the flag
	entirely — `waired init` reads it from there.
</Aside>

Waired must already be installed and its background service running: an auth
key is a credential, not a way to skip the service. If the service is not
answering, `waired init` says so and stops rather than half-joining the
machine.

Setting up this way, the machine joins your network and appears in the console
straight away, but the browser setup wizard does not open for it — there is no
browser. `waired init` knows that and carries on with setup in the terminal:
it does not mention a browser, and it does not wait for one. Everything else,
including choosing its AI model, is available from the console.

<Aside type="note" title="Unattended installs route Claude Code without asking">
	There is nobody at the terminal to answer the routing question, so an
	unattended install takes the same answer an attended one defaults to: yes.
	Claude Code on that machine is pointed at Waired for **everyone who uses
	it** — it is a machine-wide setting, not a per-user one.

	To leave Claude Code on the Anthropic API instead, install with
	`--skip-claude-proxy` (`-SkipClaudeProxy` on Windows, or
	`WAIRED_NO_CLAUDE_PROXY=1` in the environment). Everything else — joining
	your network, the model, the skills and plugins — still happens. You can
	turn routing on later with `sudo waired claude enable`, and off again with
	`sudo waired claude disable`.
</Aside>

The model then downloads in the foreground with a progress bar:

```
Starting the AI engine…
Preparing to download qwen3.8-27b…
Downloading qwen3.8-27b: 41%  7.3 GB / 17.7 GB (44 MB/s)
```

The model named on those lines is the one **you** chose. When setup is
running in the browser, that is the model you picked there — not whichever
model the computer would have selected for itself.

<Aside type="note" title="If the download is still running">
	These files are tens of gigabytes, so on a slow connection this takes a
	while. What happens next depends on which half is driving:

	- **On this path** (`--no-browser`, `--non-interactive`, or no reachable
		browser) Waired hands the shell back after about ten minutes and says the
		download will finish in the background.
	- **When this terminal is driving setup** — you took it over, or no setup
		was ever started in the browser — press <kbd>Enter</kbd> any time to stop
		watching. The terminal says *“Continuing in the background — the agent
		finishes the download on its own”* and carries on with the rest of setup.
	- **When the browser is driving setup**, the terminal stays with the bar
		until the model you chose has finished downloading, so the two halves
		never disagree about whether setup is done. <kbd>Enter</kbd> does not
		leave in that case: this window is the one doing the installation.

	Either way the download belongs to the background service, not to this
	command: <kbd>Ctrl</kbd>+<kbd>C</kbd> **does not cancel it**. Check on it any
	time with `waired status`.
</Aside>

<Aside type="caution" title="“Waired hasn't started downloading … yet”">
	If the terminal says this, the model you chose in the browser has been
	asked for but nothing has begun fetching it — most often because this
	version cannot run that particular model on this computer. The terminal
	hands the shell back rather than waiting; the background service keeps
	trying.

	Run `waired models ls` to see what state each model is in, and
	`waired doctor` if it stays that way.
</Aside>

words. A fast computer can still be paired with a heavy model.

Speed is measured once per install, and again when Waired updates. To take it
again — after adding memory or a graphics card, say — re-run `waired init`.
</Expected>


The AI software could not be installed — most often no disk space, no network,
or the command was not run with administrator rights. Sign-in is unaffected:
the computer is on your network and can use the AI on your other machines
already. Fix what the message names and run the command again; setup stops
there rather than waiting for an engine that is not coming.
</Expected>

<Expected tone="bad">
```
[!] Local inference could not complete a test generation: HTTP 500
  Check `waired status`, then `waired doctor`, for the engine's own reason.

!  Waired is signed in — local AI is not answering yet
   Signed in and running — this device is on your network.
   The AI engine here could not answer a test request; the reason is above.
```

The AI software installed and started, took the model, and then could not
answer a single test request. This is different from the case above: nothing
needs installing, so running the install again changes nothing.

The line above the box is the engine's own reason, quoted as the engine gave
it. Two causes are common — the model is too large for this computer's memory,
and a graphics driver the engine cannot use. `waired status` shows which model
is loaded and how much memory this computer has; `waired doctor` reports the
engine's own state. `waired runtimes benchmark` re-runs the same test after a
change, and offers a lighter model when one would fit.

Sign-in is unaffected either way: the computer is on your network and can use
the AI on your other machines.
</Expected>

<Aside type="caution" title="A very small model on a low-memory computer">
	On a low-memory computer, setup picks the largest model that still holds a
	full coding session — which may be a very small one. It runs, and it is the
	honest best this machine can do; expect less of it than of the model on a
	larger computer. That computer can also use the AI on your other machines.
</Aside>

## Signing in from the Waired app instead

The [Waired app](/guides/waired-app/) has a **Sign in…** entry, and it does sign
this computer in.

<Aside type="caution" title="It cannot finish a first-time setup on its own">
	Installing the AI software needs administrator rights that the app cannot
	grant. On a computer that has never been set up, signing in from the app
	gets as far as the setup page and then asks you to run `waired init` in a
	terminal anyway.

	Use **Sign in…** for signing back in after a sign-out, or on a computer that
	is already set up. For a first setup, use the command above.
</Aside>

## Setting up again

Running setup again on a computer that is already signed in is safe: it
re-authenticates and reopens the setup page, and does **not** count as a new
device against your account.

On a computer that is already set up and running a model, setup asks before it
starts over:

```text
This device is already set up — Qwen3.5 2B is serving here.
Run setup again? It re-asks every question and re-measures this computer.
  No leaves this device exactly as it is. [y/N] (default: No)
```

Press Enter to leave the computer alone — nothing is changed, and `waired
status` shows what it is doing. Answer `y` to go through the whole setup again:
every question is asked afresh and the computer is re-measured, so the speed
check in step 7 may offer a different model than last time.

This question is skipped when you have already said what you want on the
command line (`--model`, `--inference-enabled`, `--share-with-mesh`) and with
`--non-interactive`.

It is still asked after a re-authentication — `waired init --force-reauth`, or a
plain `waired init` on a computer whose sign-in expired. Signing in again
happens first, so answering No leaves the computer signed in and otherwise
exactly as it was.
