Setup normally connects Claude Code for you. This page is what to do if it did
not, and how to control it afterwards.

You do not set an environment variable, edit a config file, or use an alias.
Waired writes Claude Code's machine-wide settings so Claude Code talks to your
model — the same way on Windows, macOS and Linux.

<Aside type="caution" title="Your claude.ai subscription is untouched">
	No credential is written, so your existing Claude Code sign-in and its
	subscription behaviour keep working exactly as before. Waired changes where
	requests go, not who you are signed in as.
</Aside>

## Connect it

<Steps>

1. Set up the integration:

	```sh
	waired link claude-code
	```

2. Turn on routing. **Setup already did this** unless you declined the
	routing question, chose not to connect Claude Code in the browser, or
	installed with `--skip-claude-proxy` — so this step is for turning it back
	on later:

	<Tabs syncKey="os">
		<TabItem label="macOS / Linux">
			```sh
			sudo waired claude enable
			```
		</TabItem>
		<TabItem label="Windows">
			From an administrator prompt:

			```powershell
			waired claude enable
			```
		</TabItem>
	</Tabs>

3. Start Claude Code as you normally would:

	```sh
	claude
	```

</Steps>

## Which AI answered?

The footer tells you, every turn:

<Screenshot
	src="claude-code-statusline.png"
	alt="The Claude Code footer showing the Waired status line — the current route and the local model that answered the last request."
/>

| What it says | What it means |
|---|---|
| `⚡ waired: on Waired (qwen3-8b-instruct)` | Answered by your own hardware, by that model |
| `⚡ waired: on Waired (qwen3-8b-instruct) · model not loaded` | Same, but the AI is not in memory yet — the next answer waits for it to load |
| `⚡ waired: on Waired (peer studio-desktop: qwen3.5-35b-a3b)` | Answered by another of your computers, by that model |
| `⚡ waired: on Waired (peer)` | Another of your computers will answer; none has yet this session, so there is no name to give |
| `⚡ waired: fallback → Anthropic (local disabled, no peer)` | Nothing of yours can answer — this computer's engine is off and no other computer is available |
| `⚡ waired: Waired-only (peer studio-desktop: qwen3.5-35b-a3b)` | On the `waired` route, answered by another of your computers |
| `→ waired: Anthropic` | Answered by the real Anthropic API |
| `✕ waired: agent down` | Waired is not running on this computer |
| `→ waired: Anthropic · subagents: Waired` | Subagents are going somewhere else — see below |

The peer rows matter on a computer with no engine of its own. The footer used
to describe only *this* machine, so such a computer announced a fallback to
Anthropic before any turn had run — while your other computers were in fact
answering its turns. It now says which one.

After any turn that fell back to the cloud, Claude Code also prints a one-line
notice. Nothing is ever silently redirected.

The `· subagents:` tail appears only when you have sent subagents somewhere
other than the main conversation, with `waired claude route <mode> --sub
<mode>`. Without it the footer describes both. A split you set up on purpose
is fine; the tail is there so a split you have forgotten about does not stay
invisible.

<Aside type="note" title="No status line showing?">
	A project-level `.claude/settings.json` overrides the one Waired installs.
	Run `waired claude status` inside the project — it names the file that is
	winning and gives you a line to paste into your own status-line script.
	Waired never edits your project files.
</Aside>

## Switch where requests go

Inside a session, no restart needed:

```
/waired-route waired      # your own AI only, never the cloud
/waired-route anthropic   # the real Anthropic API
/waired-route auto        # the default: prefer yours, fall back if needed
```

The change applies from your next message. The same switch from a terminal:

```sh
waired claude route                          # what is it doing now?
waired claude route anthropic --sub waired   # main in the cloud, subagents on yours
```

`--sub` is worth knowing about: Claude Code's subagents do the bulk file
reading, and keeping them on your own hardware while the main conversation uses
the cloud is a real middle ground. See
[Privacy](/concepts/privacy/#hybrid-mode-is-an-explicit-middle-ground).

A plain route puts everything back together — `waired claude route auto` moves
the main conversation *and* returns subagents to following it, and says so when
that undoes a split you had set up. Use `--main` when you want to move only the
main conversation and leave subagents where they are.

You can also change the route from the **Waired icon** → **Claude Code**, which
has separate pickers for the main conversation and subagents.

<Aside type="note" title="“waired” means your network, not this computer">
	Which of your machines actually answers is decided by `waired worker` — see
	[Add another device](/getting-started/add-a-device/#where-the-answer-comes-from).
</Aside>

## Things that surprise people

**Claude Code still shows Anthropic model names.** It offers Opus, Sonnet and
the rest as always. When a request is served by Waired, your device's active
local model answers it, whatever the session has selected. The Anthropic name
only matters for requests that actually go to the cloud.

**Waired entries also appear in `/model`.** Alongside the Anthropic names,
`/model` offers **Waired auto — 200k**, **Waired auto — 1M**, **Waired local**,
**Waired peer** and **Waired cloud**, picked from the menu you are already in.
**Waired public share** joins them once you turn Public Share on.
They show up after you connect Claude Code; restart Claude Code once to see them.
If they are missing, see
[The Waired entries are missing from /model](/troubleshooting/#the-waired-entries-are-missing-from-model).

The two **auto** entries differ only in how much conversation the session holds.
Both use your own computers when they can and Anthropic when they cannot — but a
computer is only used for one of them if it is actually running a model with room
for that much conversation. Most computers can do 200k; 1M needs far more memory
than a desktop has, so choosing it will usually mean Anthropic answers. Pick the
one that matches the work: 200k for ordinary sessions, 1M when you are handing
Claude Code an entire large codebase at once.

**Waired local** is the entry that ignores all of that and always uses this
computer, whatever it can hold. It is the one to pick when you want your own
machine to answer no matter what.

**Waired peer** is its mirror image: always one of your *other* computers,
never this one. Pick it when this machine should stay free — a laptop on
battery, or one you would rather not hear the fan on — and let a desktop
answer. It does not fall back: if no other computer can answer, the request
fails and says so, rather than quietly running here after you asked it not to.
Which of your computers answers is decided the same way it always is, so
`waired worker set --pin <computer>` still chooses a particular one. This entry
is for one conversation only — it does not change the setting `waired worker`
holds for everything else.

A computer with no inference engine of its own can use this. That is the point of it:
the machine you sit at does not have to be the machine that runs the model. On
such a computer **Waired local** is not offered at all, since there is nothing
here to run.

**Waired public share** is the same idea for [someone else's
computer](/guides/public-share/) — a machine another Waired user is lending
out, rather than one of yours. It appears only once you have turned Public
Share on and accepted its warning; until then it is simply not in the list.

It does not change the setting you made there. If you set Public Share to use
another person's machine only when it is better than your own, that still
applies, so this entry can decline — and when it does it says which of the two
reasons it was: no public machine was reachable, or none was better than what
you already have.

**Your other computers are listed by name too.** Below the entries above,
`/model` carries a row for each computer currently able to answer, with the
model it is running:

```
Waired peer: studio-desktop (qwen3.5-35b-a3b)
Waired peer: attic-server (qwen3.5-122b-a10b)
```

Picking one sends the conversation to that machine, and only that machine. Two
things to know about them:

- **The list is rebuilt every time you start Claude Code.** A computer you
  switched on a minute ago is there the next time you run `claude`. It is not
  rebuilt *during* a session, though: re-opening `/model` in a running one
  shows the list Claude Code read when it started. If you pick a computer that
  has since gone away, the request fails and names it rather than quietly going
  somewhere else.
- **Only computers that can answer right now are listed.** One that is off,
  still downloading, or has no engine is left out, because the menu has no way
  to show a row as unavailable.

`waired claude status` shows how many entries were written and when.

**Long sessions get summarized.** Models hold less conversation at once than the
cloud does, so Claude Code compacts older turns to fit. The two **auto** entries
each state their limit up front, and a computer only answers for one of them if
it really has that much room, so the summarizing happens where you expect.
**Waired local** is the exception: it uses whatever this computer can hold, so
if you switch to a different model later, run `sudo waired claude enable` again
(Windows: from an administrator prompt) so the new limit is passed on —
`waired claude status` shows both numbers and says when they disagree. That is
the session surviving, not failing — see
[Long Claude Code sessions get summarized](/troubleshooting/#long-claude-code-sessions-get-summarized).

**Some models hold much less than others.** A few in the catalog — the
`gpt-oss` pair — tops out around 131,000 tokens instead of
200,000. Waired never picks one for you and marks them in the model list, but
they are yours to choose. If you do, Claude Code will hit the limit sooner than
it expects to; it recovers by summarizing and carrying on, but summarizing under
pressure loses more than summarizing early does. Have it start earlier:

```sh
export CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=55
```

55–60 is the useful range with a 131k model. This is a Claude Code setting, not
a Waired one — it may change with their releases, and it does nothing on a model
that already holds a full session.

**Failures fall back rather than break.** If your model cannot serve a request —
paused, still downloading, an unsupported request shape — Claude Code uses the
real Anthropic API so your turn completes. Choose the `waired` route if you
would rather see the error than have it redirected.

**A slow computer is not a failure.** The first turn of a session is the
expensive one: the whole conversation, your instructions and the file contents
have to be read before a single word comes back, and on a laptop or an older
graphics card that can take several minutes. Waired does not give up on it. For
as long as the computer answering keeps reporting that it is working, the turn
waits — what ends it is that computer saying it has stopped, going quiet
altogether, or ten minutes passing. Only then does the turn go to the real
Anthropic API, with a note saying which of those happened.

Later turns in the same session are far quicker, because the part that was
already read does not have to be read again.

**A pinned computer is never substituted.** If you pinned one of your machines
with `waired worker` and it is unavailable, Waired does not answer from this
computer instead. On the `auto` route the turn goes to the real Anthropic API,
with a note in the conversation saying why; on the `waired` route it fails. See
[Requests stopped working after I pinned a computer](/troubleshooting/#requests-stopped-working-after-i-pinned-a-computer).

## Sharing one machine with your other devices

In the [web console](https://app.waired.ai/), a machine's page decides how the
rest of your devices may use it:

- **Serve main / subagents** — two switches. Turning main off keeps a slower
  machine for parallel subagent work only. This affects requests from *other*
  machines; the machine always serves its own Claude Code.
- **Max concurrent requests** — how many requests it handles at once. More
  parallelism needs more memory and slows every request, so the page shows a
  recommended maximum and warns before you pass it.

## Check it, or remove it

```sh
waired claude status
```

Reports whether routing is on, and where the settings file lives:

| | |
|---|---|
| Linux | `/etc/claude-code/managed-settings.json` |
| macOS | `/Library/Application Support/ClaudeCode/managed-settings.json` |
| Windows | `C:\Program Files\ClaudeCode\managed-settings.json` |

It also checks that the status line and the fallback notice are written in a form
this computer can run. Claude Code starts them through a shell, and which shell
that is differs by operating system — on Windows it is Git Bash where Git Bash is
installed and PowerShell where it is not. Waired versions before this one wrote
the same Unix form everywhere, so on a Windows computer without Git Bash both
were installed and silently did nothing. If `waired claude status` says
`installed, but not in the form this computer runs`, or `waired doctor` warns
about it, one command rewrites both:

```sh
sudo waired claude enable    # Windows: from an administrator prompt
```

To stop routing Claude Code through Waired — this restores Claude Code's normal
behaviour:

```sh
sudo waired claude disable    # Windows: from an administrator prompt
```

To remove the integration files as well:

```sh
waired unlink claude-code
```
